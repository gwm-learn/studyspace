# UDP协议

> 深入阅读可参考 [《计算机网络·运输层》](./../../1.知识体系/1.计算机网络/m-3-运输层--.md)

## 一、UDP概述

UDP（User Datagram Protocol，用户数据报协议）位于运输层，与 TCP 一起承载于 IP 层之上，端口号 0 到 65535。它面向无连接，发送方不需要与接收方建立连接就能直接发送数据，因此被称为"尽力而为"的传输服务。

UDP 的四大特点：

| 特点 | 说明 |
|------|------|
| 无连接 | 发送前不需要握手，开销小、时延低，也意味着没有连接状态需要维护 |
| 不可靠 | 不保证送达、不保证顺序、不重传，丢包由上层应用自行处理 |
| 低开销 | 头部只有 8 字节，协议栈处理简单，适合高频小报文场景 |
| 面向报文 | 一次发送一个完整的报文，应用层交付多少数据，UDP 就原样封装多少，不拆分也不合并 |

面向报文这一点和 TCP 的字节流完全不同。TCP 把应用层数据当成连续的字节流，自行决定如何分段；UDP 则保留报文的边界，接收方每次 read 得到的正好是一个完整的 UDP 报文。

## 二、UDP报文格式

UDP 头部固定 8 字节，结构非常简单：

| 字段 | 长度 | 说明 |
|------|------|------|
| 源端口 | 2 字节 | 发送方端口，可选，不需要回复时可为 0 |
| 目的端口 | 2 字节 | 接收方端口，用于分用，把报文交给对应的应用进程 |
| 长度 | 2 字节 | UDP 报文总长度，含 8 字节头部，最小 8，最大 65507 |
| 校验和 | 2 字节 | 检验整个报文在传输中是否出错，可选，IPv4 下可为 0 |

UDP 报文格式示意：

```
 0                   16                  31
+-------------------+-------------------+
|    源端口(16)     |    目的端口(16)    |
+-------------------+-------------------+
|     长度(16)      |    校验和(16)      |
+-------------------+-------------------+
|           数据（可变长度）            |
+--------------------------------------+
```

长度字段的上限来自 IP 数据报：IP 最大长度 65535 字节，减去 IP 头部（最小 20 字节）和 UDP 头部（8 字节），UDP 数据部分最多 65507 字节。

## 三、UDP校验和计算

UDP 校验和覆盖三个部分，除了自己的报文，还要把伪首部也算进来：

```
校验和覆盖范围 = 伪首部 + UDP头部 + 数据
```

伪首部并不真正出现在报文里，它只是从 IP 头部借来的 12 字节，用于把 IP 层的地址信息纳入校验：

| 字段 | 长度 | 来源 |
|------|------|------|
| 源IP地址 | 4 字节 | 取自 IP 头部 |
| 目的IP地址 | 4 字节 | 取自 IP 头部 |
| 保留 | 1 字节 | 固定为 0 |
| 协议号 | 1 字节 | UDP 固定为 17 |
| UDP长度 | 2 字节 | 与 UDP 头部中的长度字段一致 |

计算过程如下：

1. 把伪首部和 UDP 报文按 16 位一组拼起来；
2. 数据部分不足 16 位的倍数时，末尾补 0 字节（只用于计算，不实际发送）；
3. 对每一组 16 位字做二进制反码求和；
4. 对求和结果取反码，填入校验和字段。

接收方用同样的方法求和，若结果为全 1 则校验通过。伪首部的存在保证了一个 UDP 报文不会被转发到错误的 IP 地址或错误的协议栈上。IPv6 下的校验和是强制的，且伪首部结构略有不同。

## 四、UDP与TCP对比

| 对比项 | UDP | TCP |
|--------|-----|-----|
| 连接 | 无连接 | 面向连接，三次握手 |
| 可靠性 | 不可靠，不重传 | 可靠，确认、重传、排序 |
| 头部大小 | 8 字节 | 20 字节起，可带选项 |
| 传输方式 | 面向报文 | 面向字节流 |
| 流量控制 | 无 | 滑动窗口 |
| 拥塞控制 | 无 | 有 |
| 传输模式 | 单播、组播、广播都支持 | 仅单播 |
| 应用场景 | 实时、简单查询 | 可靠文件传输等 |

UDP 把可靠性问题交给上层，换来的是低时延和简单的实现，适合对实时性敏感、对少量丢包不敏感的应用。

## 五、典型应用场景

| 协议 | 端口 | 说明 |
|------|------|------|
| DNS | 53 | 域名解析查询，请求应答式，一个报文一次交互 |
| DHCP | 67（服务器）/ 68（客户端） | 客户端在无 IP 时也能通过广播收发配置信息 |
| SNMP | 161（查询）/ 162（Trap） | 网络设备管理，监控告警不重传 |
| NTP | 123 | 网络时间同步，周期上报时钟偏差 |
| RTP / RTCP | 动态（偶数/奇数成对） | 音视频实时传输，RTCP 负责质量反馈 |
| TFTP | 69 | 简单文件传输，靠超时重发实现"半可靠" |
| QUIC | 443 | 新一代传输协议，见下文 |

DNS、DHCP、SNMP 都属于"一问一答"的短交互，用 UDP 一次搞定，省去握手开销。NTP 和 RTP 是典型的实时业务，宁可丢一帧也不能等重传。注意 DHCP 和 RTP 依赖 UDP 的广播、组播能力，这是 TCP 无法提供的。

## 六、QUIC简介

QUIC（Quick UDP Internet Connections）是 Google 提出、IETF 标准化的传输协议，运行在 UDP 之上，把可靠的传输逻辑全部搬到用户态实现。

核心设计：

| 特性 | 说明 |
|------|------|
| 可靠传输 | 在 UDP 之上自行实现确认、重传、排序和拥塞控制 |
| 多路复用 | 一个连接内多个流相互独立，一个流丢包不影响其他流 |
| 0-RTT握手 | 复用上次会话的凭证，首包即可携带数据，省掉一次往返 |
| 连接迁移 | 连接标识与 IP 解耦，WiFi 与蜂窝切换不断连 |
| 内建加密 | TLS 1.3 融入握手，默认加密 |

QUIC 是 HTTP/3 的底层传输协议。HTTP/2 虽然解决了队头阻塞的应用层问题，但 TCP 丢包重传仍会让整个连接停顿，而 QUIC 用独立流避免了这个问题。由于 UDP 在中间设备上普遍放行，QUIC 也规避了 TCP 被运营商干扰的问题。

## 七、小结

- UDP 用 8 字节头部换来低开销、低时延，代价是不保证送达；
- 校验和用伪首部把 IP 地址纳入保护范围，保证报文不被送错主机；
- 实时业务和简单查询首选 UDP，可靠传输则交给 TCP 或上层的 QUIC；
- QUIC 站在 UDP 的肩膀上，把可靠性搬到用户态，成为 HTTP/3 的基石。
