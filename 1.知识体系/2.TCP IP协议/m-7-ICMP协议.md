# ICMP协议详解

## 1. ICMP概述

网际控制报文协议（Internet Control Message Protocol，ICMP），是IP协议族中的配套协议，工作在**网络层**。IP协议本身只负责"尽力而为"地转发数据报，既不保证可靠交付，也不提供任何差错反馈；ICMP正是为弥补这一缺陷而设计，它充当IP协议的"**诊断工具**"和"**差错报告员**"。

- ICMP报文封装在IP数据报中传输，其协议号（IP Header 中的 Protocol 字段）为 **1**。
- ICMP不是传输层协议，它不承载用户数据，只是传输**控制信息**和**差错信息**。
- ICMP报文由**源主机的IP层**负责封装与发送，由**目的主机的IP层**接收并处理，对应用程序透明。
- ICMP有IPv4（ICMPv4）和IPv6（ICMPv6）两个版本，分别定义在 RFC 792 和 RFC 4443 中。本文第1~5章讲ICMPv4，第6~7章讲ICMPv6。

> ICMP与IP的关系可以类比为"IP负责寄快递，ICMP负责报告快递路上出了什么问题"。

### 1.1 ICMP的两个基本功能

| 功能 | 说明 |
|------|------|
| **差错报告** | 当IP数据报在传输过程中出现差错（如目的不可达、TTL耗尽、参数错误）时，路由器或目的主机向源主机报告错误原因 |
| **网络诊断/查询** | 主动探测网络连通性（ping）和路由路径（traceroute），以及通告时间戳、地址掩码等信息 |

> 重要规则：**差错报告报文本身携带的IP数据报如果又出错了，则不再继续产生差错报文**（防止无限递归）。同样，对差错报文的回应也不再产生差错报文。

## 2. ICMPv4报文格式

所有ICMPv4报文的前4字节是固定格式：**Type（1字节）+ Code（1字节）+ Checksum（2字节）**，之后才是与具体类型相关的报文主体。整个ICMP报文被封装进IP数据报（Protocol=1）中传输。

| 字段 | 长度 | 说明 |
|------|------|------|
| Type（类型） | 1字节 | 标识报文类型，如 0=回显应答、8=回显请求、3=目的不可达 |
| Code（代码） | 1字节 | 在同一类型下进一步细分，如 Type 3 的 Code 0~15 表示不同的不可达原因 |
| Checksum（校验和） | 2字节 | 覆盖整个ICMP报文（含头部和数据部分），用于检测传输错误 |
| 报文主体 | 不定 | 与类型相关，差错报文通常携带出错IP数据报的头部及其前8字节数据 |

> 差错报文的"报文主体"部分会**回显触发错误的IP数据报头部及其前8字节数据**。这8字节通常是TCP/UDP端口号，便于源主机确定是哪条连接出了问题。

## 3. ICMPv4类型/代码速查表

| Type | 名称 | Code | 说明 |
|------|------|------|------|
| **0** | Echo Reply（回显应答） | 0 | ping的应答报文 |
| **3** | Destination Unreachable（目的不可达） | 0~15 | 目的不可达的细分原因 |
| 4 | Source Quench（源点抑制） | 0 | 通知源主机放慢发送速度（已废弃） |
| 5 | Redirect（重定向） | 0~3 | 告诉源主机"有更优的路由路径" |
| **8** | Echo Request（回显请求） | 0 | ping的请求报文 |
| 9 | Router Advertisement（路由器通告） | 0 | 路由器定期通告自己的存在 |
| 10 | Router Solicitation（路由器请求） | 0 | 主机主动请求路由器通告 |
| **11** | Time Exceeded（超时） | 0=TTL耗尽，1=分片重组超时 | traceroute的核心机制 |
| 12 | Parameter Problem（参数问题） | 0~2 | IP头部参数错误或缺失选项 |
| 13 | Timestamp Request（时间戳请求） | 0 | 请求对方回送时间戳 |
| 14 | Timestamp Reply（时间戳应答） | 0 | 应答时间戳请求 |
| 17 | Address Mask Request（掩码请求） | 0 | 请求子网掩码（已废弃） |
| 18 | Address Mask Reply（掩码应答） | 0 | 应答掩码请求（已废弃） |

### 3.1 Type 3 目的不可达（重点）

Type 3 是实际组网中最常见的差错报文，通过 Code 字段细分原因（Code 0~15）：

| Code | 含义 | 说明 |
|------|------|------|
| 0 | 网络不可达 | 路由器没有到达目的网络的路由 |
| 1 | 主机不可达 | 目的网络可达，但目的主机不可达 |
| 2 | 协议不可达 | 目的主机不支持IP头部中指定的上层协议 |
| 3 | 端口不可达 | 目的主机的对应UDP/TCP端口未开放（traceroute依赖它） |
| 4 | 需要分片但DF置位 | 报文超过链路MTU且不允许分片（IPv4路径MTU发现的依据） |
| 5 | 源路由失败 | 源路由选项指定的路径不可用 |
| 6 | 目的网络未知 | 与Code 0类似，但表示完全未知 |
| 7 | 目的主机未知 | 与Code 1类似，但表示完全未知 |
| 8 | 源主机被隔离 | 源主机被管理性隔离 |
| 9 | 与目的网络的通信被禁止 | 管理性策略禁止访问该网络 |
| 10 | 与目的主机的通信被禁止 | 管理性策略禁止访问该主机（防火墙常见） |
| 11 | 对特定类型服务网络不可达 | 按服务类型（TOS）不可达 |
| 12 | 对特定类型服务主机不可达 | 按服务类型（TOS）不可达 |
| 13 | 通信被管理性禁止 | 通用管理性禁止（防火墙拦截的典型应答） |
| 14 | 主机优先级冲突 | 主机优先级设置冲突 |
| 15 | 优先级被截断 | 目的网络切断了优先级服务 |

### 3.2 Type 5 重定向

当路由器发现数据报应该从**另一个路由器**转发时，会向源主机发送重定向报文，告诉源主机"以后发往该目的地的数据请直接交给××"，从而优化路由。Code 0~3 分别表示：对网络重定向、对主机重定向、对网络和服务类型重定向、对主机和服务类型重定向。

> 重定向只影响源主机后续的**新连接**，已建立的连接不受影响。重定向报文可能被攻击者伪造用于流量劫持，多数主机默认只接受来自当前网关的重定向。

### 3.3 Type 11 超时

Type 11 的 Code 0 表示传输期间TTL字段为0（TTL耗尽），由路由器产生；Code 1 表示分片重组时间超时，由目的主机产生。

> TTL（Time To Live，生存时间）：IPv4数据报每经过一台路由器减1，减到0时报文被丢弃，并由该路由器返回 Type 11 Code 0 的ICMP报文。TTL机制防止数据报在网络中无限循环。

## 4. ping原理详解

ping 是最常用的网络连通性测试工具，基于ICMP **回显请求（Echo Request，Type 8）** 和 **回显应答（Echo Reply，Type 0）** 报文实现。

### 4.1 工作流程

1. ping程序构造一个ICMP回显请求报文，填入**标识符（Identifier）**和**序号（Sequence Number）**，并记录发送时刻 t1。
2. 该报文被封装进IP数据报发往目标主机。中间经过的路由器只做转发，不回应（TTL正常时）。
3. 目标主机收到后，把请求报文原样作为应答内容，立即回送一个ICMP回显应答报文（Type 0）。
4. 源主机收到应答，记录接收时刻 t2，计算 **RTT（往返时延）= t2 − t1**，并解析出应答IP数据报中的 **TTL** 值。

> 报文交换简记为：`Echo Request(Type 8) ──► 主机B ──► Echo Reply(Type 0) ◄──`，应答内容为请求报文原样回填。

### 4.2 ping输出的关键信息

| 信息 | 含义 |
|------|------|
| RTT（往返时延） | 数据报往返一次所花时间，反映链路延迟和拥塞程度 |
| 应答中的TTL | 由发送时TTL（通常64/128）减去途经路由器数得出，可粗略推断对方操作系统 |
| 丢包率 | 请求发出但未收到应答的比例，衡量链路质量 |

> 注意：应答报文中的TTL是**目标主机发送时的初始TTL减去返回路径经过的路由器数**，并非发送方发出的TTL。Linux默认TTL为64，Windows为128，据此可大致推断对端系统类型。
>
> 若目标主机禁止响应ICMP（如防火墙丢弃），ping会显示超时（Request timed out），此时**不能简单断定主机不可达**，目标可能只是"不回应"，服务仍可正常访问。

## 5. traceroute原理详解

traceroute（Windows下为 tracert）用于探测从源主机到目标主机经过的**每一跳路由器**，其原理巧妙结合了**TTL递增**与 **UDP+ICMP端口不可达** 两个机制。

### 5.1 核心原理

1. traceroute向目标主机发送**UDP数据报**，选择一个**高端口号**（如33434起递增），IP头部的TTL从 **1 开始逐次递增**。
2. 第n跳路由器收到TTL=n的数据报时，TTL减1变为0，于是丢弃该报文，并回送一个 **ICMP超时报文（Type 11，Code 0）**。报文中带有该路由器的源IP地址。
3. traceroute根据收到的ICMP超时报文，就知道第n跳路由器的IP地址，并测出到达该跳的RTT。
4. 当UDP数据报最终到达目标主机时，TTL尚未耗尽，但目标主机上没有监听该高端口的UDP服务，于是回送一个 **ICMP端口不可达报文（Type 3，Code 3）**。
5. traceroute收到端口不可达报文，即确认已到达终点，探测结束。

> 探测过程简记为：TTL=1 被第1跳路由器丢弃并回ICMP超时，TTL=2 被第2跳丢弃并回ICMP超时，……直到TTL=n 到达主机B，因其UDP高端口无人监听而回ICMP端口不可达。

### 5.2 关键细节

| 细节 | 说明 |
|------|------|
| 每跳发送多个探测包 | 默认发3个，取3次RTT显示，反映链路稳定性 |
| UDP端口选择 | 从33434起每跳递增，尽量避免与目标主机现有UDP服务冲突 |
| 结束条件 | 收到ICMP端口不可达（到达目标）或达到最大跳数（默认30） |
| 与ping的区别 | ping只测"通不通"，traceroute测"经过哪些路、每一跳多快" |

> traceroute的变体：Linux下还可用 `traceroute -I`（用ICMP回显请求代替UDP）和 `traceroute -T`（用TCP SYN探测）。Windows的tracert默认使用ICMP回显请求实现。当某跳路由器不回应ICMP时，该跳会显示为 `* * *`（超时），并不代表链路断开，可能只是该路由器禁止回应。

## 6. ICMPv6概述

ICMPv6（RFC 4443）是IPv6协议族的配套协议，IPv6协议号同样为 **1**。相比ICMPv4，ICMPv6发生了重大变化：它不再只是"诊断工具"，而是**IPv6正常运行不可或缺的核心组件**。

### 6.1 ICMPv6与ICMPv4的主要差异

| 对比项 | ICMPv4 | ICMPv6 |
|--------|--------|--------|
| 类型号重新编号 | Type 0~18 | 类型号重新规划，取消"请求/应答"成对编号，改为按奇偶划分 |
| 差错报文 | 一般 | **ICMPv6差错报文（Type 128以下）的源地址必须是链路本地地址** |
| 邻居发现 | 由ARP实现 | 内建 **NDP（邻居发现协议）**，取代ARP |
| 组播管理 | 由独立的IGMP实现 | 内建 **MLD（组播监听发现）**，取代IGMP |
| 路径MTU发现 | 依赖路由器 | 内建 **PMTU发现**（Type 2 包太大报文驱动） |
| 请求/应答编号 | 8/0、13/14 成对 | Echo为128/129，其它查询类基本取消 |
| 分片 | 路由器可分片 | **路由器不分片**，靠发送端PMTU发现，因此包太大报文至关重要 |

> ICMPv6的差错报文"源地址必须是链路本地地址"这一要求，是IPv6安全模型的一部分，用于防止跨网段的伪造差错报文攻击。

### 6.2 ICMPv6报文格式

与ICMPv4相同的前4字节结构：**Type（1字节）+ Code（1字节）+ Checksum（2字节）**。但ICMPv6的**校验和必须包含伪头部**（IPv6源地址、目的地址、长度和下一跳头）参与计算，这一点与ICMPv4不同。

## 7. ICMPv6关键类型

| Type | 名称 | Code | 说明 |
|------|------|------|------|
| 1 | Destination Unreachable（目的不可达） | 0~4 | 0=无路由，1=被管理性禁止，2=超出源地址范围，3=地址不可达，4=端口不可达 |
| 2 | Packet Too Big（包太大） | 0 | 报文超过链路MTU，报文中携带实际MTU值，**PMTU发现的核心** |
| 3 | Time Exceeded（超时） | 0=跳数耗尽，1=分片重组超时 | 对应ICMPv4的Type 11 |
| 4 | Parameter Problem（参数问题） | 0~2 | 头部字段错误、未知选项等 |
| 128 | Echo Request（回显请求） | 0 | 对应ICMPv4 Type 8，ping使用 |
| 129 | Echo Reply（回显应答） | 0 | 对应ICMPv4 Type 0 |
| 130 | Multicast Listener Query（组播监听查询） | 0 | MLD查询 |
| 131 | Multicast Listener Report（组播监听报告） | 0 | MLD报告 |
| 132 | Multicast Listener Done（组播监听离开） | 0 | MLD离开 |
| 133 | Router Solicitation（路由器请求，RS） | 0 | 主机启动后请求路由器发送RA |
| 134 | Router Advertisement（路由器通告，RA） | 0 | 路由器通告前缀、MTU、跳数限制等信息 |
| 135 | Neighbor Solicitation（邻居请求，NS） | 0 | 对应ARP请求，解析邻居链路层地址 |
| 136 | Neighbor Advertisement（邻居通告，NA） | 0 | 对应ARP响应，应答邻居请求 |

### 7.1 邻居发现协议（NDP，Type 133~136）

NDP（Neighbor Discovery Protocol，RFC 4861）用四个ICMPv6报文实现了IPv4中由ARP、ICMP重定向、路由器发现等多个协议完成的功能：

| 报文 | 作用 | 对应IPv4机制 |
|------|------|--------------|
| **RS（133）** | 主机启动时请求网络中的路由器发送RA | ICMP路由器请求（Type 10） |
| **RA（134）** | 路由器周期性或回应RS，通告前缀/MTU/网关信息，实现无状态地址自动配置（SLAAC） | ICMP路由器通告（Type 9）+ DHCP |
| **NS（135）** | 询问邻居的链路层地址，同时做重复地址检测（DAD） | ARP请求 |
| **NA（136）** | 应答NS，通告自己的链路层地址 | ARP响应 |

> NDP取代ARP是IPv6的重大改进之一：NS/NA使用组播而不是广播，且NDP报文自带认证和防重放机制（Secure Neighbor Discovery），从设计上削弱了ARP欺骗这类攻击。

### 7.2 MLD（组播监听发现，Type 130~132）

MLD（Multicast Listener Discovery，RFC 2710，RFC 3810为MLDv2）在功能上等价于IPv4的IGMP，用于组播路由器维护接口上组播组成员关系，由ICMPv6报文承载。

## 8. ICMP安全问题

ICMP设计于"网络可信"的年代，未考虑安全需求，因此成为多种攻击手段的载体。

### 8.1 ICMP Flood攻击

| 攻击 | 原理 | 危害 |
|------|------|------|
| **ICMP Flood（ICMP洪水）** | 攻击者向目标主机发送海量ICMP回显请求（或应答），耗尽目标的CPU和带宽资源 | 目标无法处理正常业务，形成拒绝服务（DoS） |
| **Ping Flood** | ICMP Flood的特例，专指洪水式发送ping报文 | 同ICMP Flood，是最常见的形式 |

> 防护：限制ICMP速率（rate-limit）、在边界过滤ICMP、部署流量清洗设备。

### 8.2 Smurf攻击

Smurf攻击利用ICMP的**广播放大**特性：攻击者伪造源IP为**受害主机IP**，向一个**广播地址**（如 ping 255.255.255.255）发送ICMP回显请求；该广播域内所有主机收到请求后，都把应答发往受害主机。一份请求被放大成几十上百份应答，形成**反射放大攻击**，使受害主机被大量无关应答淹没。

> 防护：路由器关闭IP广播转发、配置 no ip directed-broadcast（思科等设备）、在边界过滤ICMP广播请求。

### 8.3 Ping of Death（死亡之ping）

利用ICMP报文**分片重组**的漏洞：早期操作系统对IP分片重组时的**缓冲区长度**检查不严，攻击者发送大量超长（超过65535字节上限）的ICMP回显请求分片；接收方重组这些分片后缓冲区溢出，导致**系统崩溃、重启或内核死锁**。

> 该漏洞在上世纪90年代非常出名，现代操作系统已修复了重组边界检查。但同类"利用分片/超大报文"的变种思路仍存在于协议设计中，是IPv4分片机制安全性不足的例证。

### 8.4 其它ICMP安全威胁与防护

| 威胁/防护 | 说明 |
|-----------|------|
| ICMP重定向攻击 | 伪造Type 5报文把受害主机的流量重定向到攻击者，实现中间人攻击 |
| ICMP隧道 | 把数据隐藏在ICMP Echo报文的数据区中传输，绕过防火墙（如ptunnel工具） |
| 差错报文DoS | 伪造Type 3/11报文，干扰合法TCP连接（切断路径MTU发现，使大报文无法通过） |
| 限制ICMP速率 | 对ICMP报文做限速，防止洪水淹没CPU |
| 边界过滤 | 在网关上过滤不需要的ICMP类型（如入方向的Echo Request、Redirect） |
| 关闭广播应答 | 禁止对广播地址的ICMP请求进行应答（防Smurf） |
