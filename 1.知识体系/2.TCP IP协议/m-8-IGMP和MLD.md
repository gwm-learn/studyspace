# IGMP 和 MLD 协议详解

## 1. 组播基础概念

组播（Multicast）是一对多的通信方式，发送者只发一份数据，路由器沿组播分发树复制转发给所有接收者。相比单播逐台发送、广播全网泛洪，组播在"多接收者、接收者动态变化"的场景（IPTV、视频会议、网络游戏）中效率最高。

组播模型涉及两类角色：**组成员**（主机，通过 IGMP/MLD 加入或离开组）与**组播路由器**（最后一跳路由器通过 IGMP/MLD 感知组成员，路由器之间靠 PIM 等协议构建分发树）。

> 一句话概括分工：**IGMP/MLD 解决"谁想收"（主机与最后一跳路由器之间），PIM 解决"怎么送"（路由器之间）**。

### 1.1 组播地址

| 协议 | 组播地址范围 | 说明 |
|------|-------------|------|
| IPv4 | 224.0.0.0/4（D 类） | 高 4 位固定为 1110，即 224.0.0.0 ~ 239.255.255.255 |
| IPv6 | FF00::/8 | 高 8 位固定为 FF，后 4 位标志 + 4 位作用域 |

| 特殊组播地址 | 含义 |
|-------------|------|
| 224.0.0.1 / FF02::1 | 本链路所有主机（所有节点） |
| 224.0.0.2 / FF02::2 | 本链路所有路由器 |
| 224.0.0.5 / FF02::5 | OSPF 路由器 |
| 224.0.0.22 / FF02::16 | 本链路所有 IGMPv3/MLDv2 路由器 |
| 232.0.0.0/8、FF3x::/32 | SSM（指定源组播）专用范围 |
| 239.0.0.0/8 | IPv4 本地管理组播地址（私网内使用） |

224.0.0.0/24 为**链路本地**组播地址，TTL=1，只在本地子网内传播，不参与路由。

### 1.2 组播 IP → 组播 MAC 映射

以太网单播 MAC 是设备唯一，组播 MAC 则由组播 IP 映射而来，保证网卡能按 MAC 过滤帧：

| 协议 | OUI 前缀 | 映射规则 | 示例 |
|------|----------|----------|------|
| IPv4 | **01-00-5E** | 组播 IP 的**低 23 位**拼接到 `01:00:5E:00:00:00` 后 | 239.1.1.1 → 01-00-5E-01-01-01 |
| IPv6 | **33-33** | 组播 IP 的**低 32 位**拼接到 `33:33:` 后 | FF02::1 → 33-33-00-00-00-01 |

两个注意点：

- IPv4 组播地址共 28 位组播 ID，MAC 只映射低 23 位，**高位 5 位不参与映射**，因此 32 个组播 IP 会映射到同一个组播 MAC（如 224.0.0.1 与 224.128.0.1 相同）。网卡收到帧后需上送协议栈，由 IP 层再过滤一次
- 以太网 IANA 规定 `01:00:5E:00:00:00 ~ 01:00:5E:7F:FF:FF` 全部属于组播；OUI 之后 MAC 的第 25 位固定为 0

## 2. IGMP 概述

**IGMP（Internet Group Management Protocol，因特网组管理协议）**是 IPv4 下主机与路由器之间的组成员管理协议，运行在 IP 之上、传输层之下，**协议号 2**，直接封装于 IP 报文中。

| 版本 | RFC | 核心能力 |
|------|-----|----------|
| **IGMPv1** | RFC 1112 | 最基本的加入/查询/响应机制 |
| **IGMPv2** | RFC 2236 | 增加快速离组、特定组查询、查询器选举 |
| **IGMPv3** | RFC 3376 | 支持指定源过滤（SSM 前提） |

## 3. IGMPv1：基本的加入与查询

IGMPv1 只有两种报文：

- **Membership Query（0x11）**：查询器周期（默认 125 秒）向 `224.0.0.1`（所有主机）发送，询问"谁还在组里"
- **Membership Report（0x12）**：主机收到查询后，向**组地址本身**发送报告，声明"我是该组成员"

补充机制：

- **响应抑制（Response Suppression）**：同一链路上多台主机属于同一组时，第一台主机报告后，其余主机通过报告的目的地址（组地址）**窃听**到后不再重复报告，从而减少流量
- **离组无声**：v1 **没有 Leave 消息**。主机离组时不通知任何人，路由器只能等查询周期超时（最长约 2 倍查询周期）后认为组内已无成员，才停止转发。组播流会"残留"一段时间

## 4. IGMPv2：快速离组与查询器选举

IGMPv2（RFC 2236）在 v1 基础上主要增加：

- **Leave Group 消息（0x17）**：主机离组时主动通知路由器，目的地址 `224.0.0.2`（所有路由器），实现**快速离组**
- **特定组查询（Group-Specific Query）**：收到 Leave 后，路由器针对该组发送查询，确认是否还有成员；组地址字段填入该组地址，目的地址仍为 `224.0.0.1`
- **最大响应时间（Max Response Time）**：查询报文中携带，主机在此时间内随机延迟后响应，避免同时爆发；也用于加快离组确认
- **查询器选举（Querier Election）**：多台路由器同时存在时，IP 地址**最小者获胜**成为查询器，其余路由器停止发送查询，保证链路内只有一个查询器

| 对比项 | IGMPv1 | IGMPv2 |
|--------|--------|--------|
| 离组通知 | 无，靠查询超时 | Leave Group 消息，快速离组 |
| 特定组查询 | 无 | 有 |
| 最大响应时间 | 固定 | 可调 |
| 查询器选举 | 无（指定） | 最小 IP 选举 |
| 报告目的地址 | 组地址 | 组地址；Leave 发往 224.0.0.2 |

## 5. IGMPv3：指定源过滤与 SSM

IGMPv3（RFC 3376）的核心变化是**由"只报组"升级为"报组 + 源列表"**，主机可以精确表达"我要哪个源的流量"：

- **INCLUDE 模式（包含）**：`INCLUDE {S1, S2}`，只接收列表中的源，属于"白名单"
- **EXCLUDE 模式（排除）**：`EXCLUDE {S1}`，接收除列表中源以外的所有源，属于"黑名单"，用于实现"全收但屏蔽某源"
- **源列表（Source List）**：每条组记录携带一或多个源地址
- **报告变化**：报告报文类型变为 **0x22**，目的地址 `224.0.0.22`，可在一个报文中携带**多个组记录**（每条组记录形如 `Record Type + Number of Sources + Multicast Address + Source Addresses`），并要求主机在状态变化时**主动发报告**；v3 的 Query 也在通用字段后追加源地址列表等字段

基于 IGMPv3 的 **SSM（Source-Specific Multicast，指定源组播）**：接收者必须同时指明组与源，组播流量只从指定源分发，杜绝了"任意源广播进组"的地址冲突问题，是现代组播（IPTV 按频道拉流）的主流模型。

## 6. IGMP 报文格式

### 6.1 v1/v2 通用格式（固定 8 字节）

| 字段 | 长度(位) | 说明 |
|------|---------|------|
| **Type** | 8 | 报文类型，见下表 |
| **Max Resp Time** | 8 | v2 才有意义：最大响应时间（秒）；v1 保留为 0 |
| **Checksum** | 16 | 校验和，覆盖整个 IGMP 报文 |
| **Group Address** | 32 | 组地址：Query 中为 0（或特定组查询时为目标组），Report/Leave 中为目标组 |

### 6.2 报文类型一览

| Type 值 | 报文 | 说明 |
|---------|------|------|
| **0x11** | Membership Query | 通用查询 / 特定组查询 / 特定源组查询（v3） |
| **0x12** | Version 1 Membership Report | IGMPv1 成员报告 |
| **0x16** | Version 2 Membership Report | IGMPv2 成员报告 |
| **0x17** | Leave Group | IGMPv2 离组消息 |
| **0x22** | Version 3 Membership Report | IGMPv3 成员报告（含组记录） |

## 7. MLD 概述

**MLD（Multicast Listener Discovery，组播侦听者发现）**是 IPv6 环境下的"IGMP"，功能与 IGMP 一一对应，但实现方式不同：**MLD 不是独立协议，而是 ICMPv6 的一种报文类型**（ICMPv6 type 130~132、143），必须依赖 IPv6 链路本地地址运行。

| MLD 版本 | 对应 IGMP 版本 | RFC |
|----------|----------------|-----|
| **MLDv1** | IGMPv2 | RFC 2710 |
| **MLDv2** | IGMPv3 | RFC 3810 |

> MLD 之所以从"独立的 IP 子协议"改为"ICMPv6 的一种类型"，是因为 IPv6 本身就没有单独的多播管理协议位置，ICMPv6 已成为 IPv6 的"控制面总管"（NDP、MLD、PMTU 都挂在它下面）。

## 8. MLDv1（RFC 2710）：对应 IGMPv2

| ICMPv6 Type | 报文 | 对应 IGMPv2 |
|-------------|------|-------------|
| **130** | Multicast Listener Query | Membership Query（0x11） |
| **131** | Multicast Listener Report | Membership Report（0x16） |
| **132** | Multicast Listener Done | Leave Group（0x17） |

报文内容与 IGMPv2 几乎相同，差异仅在承载方式与地址表达：

- 目的地址：Query 发往 `FF02::1`（所有节点）；Report 发往**组地址本身**；Done 发往 `FF02::2`（所有路由器）
- 组地址字段从 32 位变为 **128 位** IPv6 组播地址
- "最大响应时间"对应字段为 **Max Response Delay（毫秒）**，位置在 ICMPv6 类型/校验和之后
- 所有 MLD 报文源地址必须是链路本地地址（或未指定地址 `::`）

## 9. MLDv2（RFC 3810）：对应 IGMPv3

MLDv2 实现与 IGMPv3 相同的**源过滤能力**，是 IPv6 下 SSM 的基础：

- 新增报文：**Version 2 Multicast Listener Report（ICMPv6 Type 143）**，用于上报"组 + 源列表"和 INCLUDE/EXCLUDE 过滤模式；一个报告可携带多个组记录
- Query 仍为 Type 130，在 128 位组地址之后扩展源地址列表等字段
- 目的地址 `FF02::16`（所有 MLDv2 路由器）
- 应用场景与 IGMPv3 一致：IPTV、源选择、SSM 组播

## 10. IGMP / MLD Snooping：二层组播优化

普通交换机对组播帧的默认处理是**在 VLAN 内泛洪**（组播 MAC 查不到 MAC 表时按广播处理），浪费带宽。

**IGMP Snooping（组播侦听）**让二层交换机"偷看"（Snoop）IGMP/MLD 报文，构建**二层组播转发表**（组地址 → 端口列表）：

1. 监听主机的 **Report**：把接收端口加入该组对应的转发端口列表
2. 监听主机的 **Leave/Done**：把端口从转发端口列表中移除
3. 监听查询器的 **Query**：维护成员老化定时器，端口超时未响应则移除
4. 数据帧到达时，只向转发表中的端口转发，**不再泛洪**

MLD 对应实现叫 **MLD Snooping**，机制相同。常见增强：**静态组播组**（手工绑定端口）、**未知组播丢弃**（表内无对应组直接丢弃）、**Fast-Leave**（收到 Leave 立即删除端口，不等特定组查询确认）。

## 11. IGMP Proxy：简化的组播路由

完整组播路由（PIM 等）对**末端接入网络**（家庭网关、CPE、楼道交换机）过于复杂，IGMP Proxy 提供轻量替代：

- 设备有两个方向接口：**上行口（WAN，面向运营商）**、**下行口（LAN，面向用户）**
- 下行口扮演**查询器**角色：周期性向用户发送查询，收集成员的 Report/Leave
- 上行口扮演**主机**角色：把用户的需求**聚合**成自己的 Report 发给上游路由器，加入对应组播组；组播数据从上行口收到后，按下行口学习的成员端口转发

```
运营商组播路由器                    CPE(IGMP Proxy)                   用户主机
        │  ◄──上行口Report(聚合)──  │  ◄──下行口Query──  │
        │                          │  ──下行口Report──►  │
        │  ──组播数据──►           │  ──组播数据──►      │
```

IGMP Proxy 只需维护"组 → 上行口/下行口"两张简单关系表，不需要路由协议和 RPF 检查，**是 CPE/家庭网关普遍采用的实现**。运营商侧对 CPE 的要求也仅是"CPE 会发 IGMP 报告"，即做一次标准的组成员管理。

## 12. IGMP 与 MLD 对照速查

| 对比项 | IGMP（IPv4） | MLD（IPv6） |
|--------|--------------|-------------|
| 承载方式 | 独立协议，IP 协议号 2 | ICMPv6 报文类型 |
| 组播地址 | 224.0.0.0/4 | FF00::/8 |
| MAC 映射前缀 | 01-00-5E（低 23 位） | 33-33（低 32 位） |
| v2 版本 | RFC 2236，Type 0x16/0x17 | MLDv1（RFC 2710），Type 130/131/132 |
| v3 版本 | RFC 3376，Type 0x22 | MLDv2（RFC 3810），Type 143 |
| 二层优化 | IGMP Snooping | MLD Snooping |
| 源过滤 | v3 起支持（SSM，232.0.0.0/8） | MLDv2 起支持（SSM，FF3x::/32） |
