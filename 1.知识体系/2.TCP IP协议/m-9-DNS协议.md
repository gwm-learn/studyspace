# DNS 协议详解

## 1. 概述：域名系统与层次化命名空间

DNS（Domain Name System，域名系统）将人类易记的域名（如 `www.example.com`）映射为机器可用的 IP 地址。它替代了早期 NIS/`/etc/hosts` 单一静态文件的方案，核心规范为 **RFC 1034**（概念）与 **RFC 1035**（实现细节）。

DNS 采用**分布式、层次化的命名空间**，域名由**点分标签（Label）**组成，从右向左级别递减：

```
                 .                          ← 根域（root，一个"点"）
                 ├── com  .org  .net        ← 顶级域 TLD（.com/.org/国家域 .cn/.jp）
                 │    └── example            ← 二级域
                 │         └── www           ← 主机名（三级及以下）
```

| 层级 | 示例 | 职责 |
|------|------|------|
| **根域** | `.` | 全球 13 组根服务器（Root Server，A~M 节点），只负责指引顶级域 |
| **顶级域 TLD** | `.com` `.org` `.cn` | 通用顶级域（gTLD）与国家顶级域（ccTLD），由 ICANN 授权管理机构运营 |
| **二级域** | `example.com` | 注册者向注册商购买的域名，可在其下自由划分 |
| **主机名** | `www.example.com` | 域内具体主机，由域管理员维护 NS 记录指向的权威服务器 |

> 域名解析是**从右往左**逐级下探的过程：先问根服务器"`.com` 归谁管"，再问 `.com` 服务器"`example.com` 归谁管"，最后问 `example.com` 的权威服务器"`www` 的 IP 是什么"。每级只负责自己范围内的**下一级**，这就是"层次化"的本质。

DNS 默认基于 **UDP 53 端口**传输（报文小、开销低），报文超过 512 字节或需区域传送（AXFR/IXFR）时改用 **TCP 53**。

## 2. 解析流程：递归查询 vs 迭代查询

解析动作分两类角色：**递归解析器（Recursive Resolver）**负责替客户端"跑腿"，**权威服务器（Authoritative Server）**只回答自己管辖域内的记录。

| 查询方式 | 发起者 | 行为 | 特点 |
|----------|--------|------|------|
| **递归查询** | 客户端 → 本地解析器 | 解析器必须给出**最终答案**，查不到就替客户端逐级去问 | 对客户端透明，结果确定 |
| **迭代查询** | 解析器 → 各级服务器 | 服务器只回答"下一级该找谁"，**不代查**，由请求方自己继续问 | 服务器无状态、压力小 |

```
客户端              本地递归解析器           根服务器          .com服务器       example.com权威
  │  ①递归查询          │                     │               │               │
  │ ─────────────────►  │                     │               │               │
  │                     │  ②迭代：com归谁管？   │               │               │
  │                     │ ──────────────────► │               │               │
  │                     │ ◄── 返回.com服务器地址 │               │               │
  │                     │  ③迭代：example.com归谁管？           │               │
  │                     │ ────────────────────────────────►    │               │
  │                     │ ◄── 返回example.com权威服务器地址 ──── │               │
  │                     │  ④迭代：www的A记录？                                │
  │                     │ ────────────────────────────────────────────────►  │
  │                     │ ◄── 返回www.example.com = 93.184.216.34 ──────────  │
  │ ◄── 最终答案 ─────── │                     │               │               │
```

- 递归解析器通常是运营商/公共 DNS（如 `8.8.8.8`、`114.114.114.114`）或本地路由器
- 权威服务器只做迭代应答，**永远不替别人递归**，这是防止 DDoS 放大（见第 7 章）的关键防线之一
- 真实场景中 ②③④ 步往往**命中缓存**直接返回，客户端体验为毫秒级

## 3. DNS 报文格式

DNS 报文由**头部（Header，固定 12 字节）+ Question + Answer / Authority / Additional** 组成，同一格式适用于查询与应答：

### 3.1 Header（12 字节）

| 字段 | 长度(位) | 说明 |
|------|---------|------|
| **Transaction ID** | 16 | 事务 ID，客户端随机生成，用它与应答匹配（查询与应答必须一致） |
| **Flags** | 16 | 标志位，见下表 |
| **QDCOUNT** | 16 | Question 区中的问题数，通常为 1 |
| **ANCOUNT** | 16 | Answer 区中的资源记录（RR）数 |
| **NSCOUNT** | 16 | Authority 区中的 RR 数（权威服务器信息） |
| **ARCOUNT** | 16 | Additional 区中的 RR 数（附加信息，如粘附记录） |

Flags 字段各位：

| 位 | 名称 | 说明 |
|----|------|------|
| 0 | **QR** | 0=查询，1=应答 |
| 1~4 | **Opcode** | 0=标准查询，1=反向查询，2=服务器状态查询 |
| 5 | **AA** | 权威应答：应答是否来自权威服务器 |
| 6 | **TC** | 截断：应答超过 512 字节被截断，提示改用 TCP |
| 7 | **RD** | 期望递归：客户端置 1，要求解析器递归查询 |
| 8 | **RA** | 可用递归：服务器声明自己支持递归 |
| 9~11 | Z | 保留位（DNSSEC 时代用于 AD、CD 位） |
| 12~15 | **RCODE** | 应答码：0=NOERROR，1=FORMERR，2=SERVFAIL，3=NXDOMAIN（域名不存在），4=NOTIMP，5=REFUSED |

### 3.2 Question 区

| 字段 | 长度 | 说明 |
|------|------|------|
| **QNAME** | 变长 | 查询的域名，每个标签前加 1 字节长度前缀，以 0 结尾（如 `www.example.com` → `03www07example03com00`） |
| **QTYPE** | 16 位 | 查询的记录类型（见第 4 章），255=ANY |
| **QCLASS** | 16 位 | 查询类别，通常为 1（IN，Internet） |

### 3.3 Resource Record（RR）

Answer / Authority / Additional 三个区共用同一种 RR 结构：

| 字段 | 长度 | 说明 |
|------|------|------|
| **NAME** | 变长 | 记录所属域名（应答中常用**压缩指针**指向 Question 的 QNAME 省字节） |
| **TYPE** | 16 位 | 记录类型（见第 4 章） |
| **CLASS** | 16 位 | 类别，通常为 1（IN） |
| **TTL** | 32 位 | 缓存存活时间（秒），见第 5 章 |
| **RDLENGTH** | 16 位 | RDATA 数据长度（字节） |
| **RDATA** | 变长 | 记录数据：A 记录为 4 字节 IPv4，AAAA 为 16 字节 IPv6，其余类型按各自格式 |

## 4. 常见 DNS 记录类型

| 类型 | 名称 | RDATA 内容 | 用途与说明 |
|------|------|-----------|-----------|
| **A** | Address | 4 字节 IPv4 | 域名 → IPv4 地址，最基础的正向解析记录 |
| **AAAA** | IPv6 Address | 16 字节 IPv6 | 域名 → IPv6 地址，可多条并存 |
| **CNAME** | Canonical Name | 目标域名 | 别名记录，指向另一域名（如 `www` → `example.com`）；CNAME 不能与其他记录共存于同一名字 |
| **MX** | Mail Exchanger | 优先级(16位)+邮件服务器域名 | 邮件路由，数值越小优先级越高，多台可做冗余 |
| **NS** | Name Server | 权威服务器域名 | 声明某域由哪些服务器负责，是"下一级怎么找"的依据 |
| **PTR** | Pointer | 目标域名 | **反向解析**：IP → 域名（存放于 `in-addr.arpa` / `ip6.arpa` 特殊域） |
| **SOA** | Start of Authority | 主服务器、负责人邮箱、序列号等 | 每个区域唯一一条，描述区域主服务器与刷新参数 |
| **TXT** | Text | 任意文本串 | 可读描述，常用于 SPF/DKIM 邮件验证、域名所有权验证 |
| **SRV** | Service | 优先级+权重+端口+目标主机 | 定位具体服务（如 SIP、LDAP），`_service._proto.domain` 命名 |

补充说明：

- **粘附记录（Glue Record）**：NS 记录指向的域名若在**被管域之下**（如 NS 指向 `ns1.example.com` 且该域自身是 `example.com`），父级会在 Additional 区附带该 NS 的 A 记录，避免"鸡生蛋"的循环依赖；**反向解析 PTR** 把 IP 反写后挂到 `in-addr.arpa` 下（如 `216.34.184.93` → `93.184.34.216.in-addr.arpa`），由 IP 段所有者维护

## 5. 缓存机制（TTL 与各级缓存）

缓存是 DNS 高性能的根基，一切缓存由记录的 **TTL（Time To Live，秒）** 驱动：

| 缓存位置 | 缓存什么 | 特点 |
|----------|----------|------|
| **本地解析器 + OS/应用缓存** | 解析结果（域名→IP） | 客户端本机（如 systemd-resolved）、浏览器各自缓存，命中则无需出网 |
| **递归解析器缓存** | 各权威服务器的应答 | 运营商/公共 DNS 共享给所有用户，命中率最高 |
| **权威服务器自身** | 不缓存（它就是真相源） | 只负责签发带 TTL 的记录 |

关键行为：

- 记录到期（TTL 归零）后**必须丢弃**，重新向上游查询，以感知记录的变更
- TTL 权衡：**太大**则域名/IP 变更后客户端长期拿到旧地址；**太小**则缓存失效频繁、查询压力大。常见 A 记录 TTL 为 300~86400 秒
- **负缓存（Negative Caching）**：NXDOMAIN（域名不存在）等**否定应答**也会被缓存（RFC 2308）；同时递归解析器对权威服务器的 NS 记录往往有自己的**隐含 TTL**（如 2 天），防止权威服务器失联后整个区域"失忆"

> 缓存同时是安全双刃剑：正常场景大幅削减查询流量，但若缓存被**投毒**（见第 7 章），错误结果会在整个 TTL 期内被"广为传播"。

## 6. 加密 DNS：DoH 与 DoT

传统 DNS 明文传输，查询内容与应答可被路径上的任何节点**窥探与篡改**。加密 DNS 在传输层解决该问题：

| 对比项 | **DoT（DNS over TLS）** | **DoH（DNS over HTTPS）** |
|--------|-------------------------|---------------------------|
| RFC | RFC 7858 | RFC 8484 |
| 传输方式 | 独立 **TCP 853** 端口上的 TLS | 复用 **HTTPS 443** 端口，走 HTTP/2 |
| 报文封装 | TLS 记录直接承载 DNS 报文 | DNS 报文作为 HTTPS 的 body（`application/dns-message`） |
| 可观测性 | 独立端口，**可被识别和封锁** | 与普通网页流量混在一起，**难以区分**（隐蔽性更好） |
| 连接管理 | 长连接 + 会话复用 | 依赖 HTTP/2 多路复用 |
| 典型配置 | 路由器/系统级（如 stubby） | 浏览器内置（Chrome/Firefox）、系统级 |
| 防护能力 | 防窃听、防篡改（防中间人） | 同左，额外具备抗封锁能力 |

两者对比一句话：

- **DoT 是"给 DNS 穿上 TLS 外套"**：协议边界清晰，适合网络设备统一管控，但传统防火墙一眼就能识别端口 853 并封锁
- **DoH 是"把 DNS 藏进网页流量"**：浏览器场景部署简单、隐蔽性强，但也带来**解析器集中化**问题（流量集中于大厂 DoH 服务器，隐私反而集中暴露），且绕过网络管理员的审计

> 无论 DoH 还是 DoT，都**只保护 DNS 查询链路本身**，不能替代 **DNSSEC**（对记录做数字签名，防止权威数据被伪造）。两者层次不同：DoH/DoT 保"运输"，DNSSEC 保"数据"。

## 7. 常见 DNS 攻击与防护

| 攻击 | 原理 | 危害 | 防护手段 |
|------|------|------|----------|
| **DNS 劫持（Hijacking）** | 攻击者篡改解析结果，指向钓鱼/恶意服务器（本地劫持、上游被黑、恶意路由器） | 用户访问被重定向，账号密码被钓 | 使用 DoH/DoT 加密链路；核对解析结果；使用可信解析器 |
| **DNS 缓存投毒（Cache Poisoning）** | 向递归解析器注入伪造的应答并**抢答**，让错误记录进入缓存（经典手法：伪造 Transaction ID + 随机源端口 + Kaminsky 攻击） | 错误结果在 TTL 期内毒害所有查询者 | 随机源端口、随机 Transaction ID；**0x20 编码**（域名大小写随机化）；**DNSSEC** 根除 |
| **DNS 放大攻击（Amplification）** | 攻击者伪造受害者 IP 作为源地址，向**开放递归服务器**发送小体积查询（如 ANY、大 TXT），服务器把大体积应答（放大几十倍）打向受害者 | 反射型 DDoS，攻击流量被放大 50~100 倍 | 服务器侧：限制递归开放范围（ACL）、响应速率限制、丢弃 ANY；全网侧：BCP38 源地址验证、关闭开放递归 |

三个关键防线：

- **DNSSEC（RFC 4033~4035）**：权威服务器用私钥对记录签名，解析器用公钥验签，从**数据源头**杜绝伪造，是缓存投毒的根治方案
- **0x20 编码**：递归解析器在查询时随机变换域名的大小写，攻击者若猜不中大小写组合就无法伪造合法应答
- **加密传输（DoH/DoT）**：挡住路径上的**被动窃听与中间人篡改**，与 DNSSEC 互补
