## 0. 前提：理解 MT7981 的 Boot 链

MT7981 是一款 Filogic 架构的 SoC（ARM Cortex-A53 双核 @ 1.3GHz），集成了 Wi-Fi 6/6E 无线模块。其启动链与 PC 架构截然不同——没有 BIOS，没有 GRUB，整个启动过程由芯片内部 ROM 中的 **BootROM** 主导：

```
┌──────────────────────────────────────────────────────────────────────┐
│  1. BootROM (芯片出厂固化，无法修改)                                  │
│     - 检测启动介质 (SPI-NAND / SPI-NOR / eMMC / SD / UART)           │
│     - 根据 boot pin 选择介质，从固定偏移加载 BL2 (Preloader)           │
│     - BL2 大小有限 (<64KB)，只做最小化初始化 (DDR 培训、DMA 配置)      │
├──────────────────────────────────────────────────────────────────────┤
│  2. BL2 = Preloader (ATF 构建，来自 arm-trusted-firmware-mediatek)   │
│     - 由 OpenWrt 源码构建 (mtk-openwrt/arm-trusted-firmware.git)     │
│     - 被 mkimage 包装，添加 MediaTek 专有头 (mtk_image 工具)          │
│     - 输出: mt7981-<bootdev>-<ddrtype>-bl2.img                      │
│     - 职责: 初始化完整 DDR、完成 DRAM 训练、设置 clocks / pinctrl      │
├──────────────────────────────────────────────────────────────────────┤
│  3. BL31 = ARM Trusted Firmware (ATF 的一部分，同样来自 ATF 源码)       │
│     - EL3 Runtime 服务: SVC 调用、电源管理、TrustZone                   │
│     - 不参与日常业务，仅在启动阶段初始化安全环境                        │
│     - 输出: mt7981-<bootdev>-<ddrtype>-bl31.bin                      │
├──────────────────────────────────────────────────────────────────────┤
│  4. U-Boot (真正的 bootloader，来自 uboot-mediatek)                    │
│     - 由 fiptool 打包为 FIP (Firmware Image Package)                 │
│     - FIP 包含: --soc-fw (BL31) + --nt-fw (U-Boot proper)            │
│     - 输出: mt7981_<device>-u-boot.fip                               │
│     - 职责: 读取启动参数、加载 kernel FIT 镜像、传递 bootargs          │
├──────────────────────────────────────────────────────────────────────┤
│  5. Kernel FIT 镜像 (UBI 卷或独立分区)                                │
│     - U-Boot 从 UBI:fit 卷加载 kernel FIT                            │
│     - FIT = Flattened Image Tree: 打包 kernel + DTB + (可选 rootfs)   │
│     - fitblk 驱动将 FIT 中的 rootfs 子镜像暴露为块设备                │
│     - Linux 从 /dev/fit0 (squashfs) 启动                              │
└──────────────────────────────────────────────────────────────────────┘
```

**与 x86 最大的区别**：x86 的 bootloader (GRUB) 是文件系统级引导器，可以读取 ext4 分区；MT7981 的 BootROM 只能从原始 Flash 偏移读取固定大小的二进制，无文件系统概念。所有分区地址、大小、类型全部硬编码在 BL2 / DTS / U-Boot 中。

## 1. 构建系统架构：从 `make world` 到镜像文件

### 1.1 顶层调用链

```
make world
 └─ target/stamp-install                (toplevel.mk:133)
      └─ target/linux/install           (target/Makefile:29, builddirs-install=linux)
           └─ target/linux/mediatek/install  (target/linux/Makefile:11)
                └─ BuildTarget = BuildKernel  (include/target.mk:391 → include/kernel-build.mk)
                     ├─ compile: $(LINUX_DIR)/.modules
                     │    └─ +make -C image compile TARGET_BUILD=   (kernel-build.mk:157)
                     │         └─ image/Makefile → $(eval $(call BuildImage))
                     │              ├─ Device/Build/kernel (DTS 编译 + KERNEL 管道)
                     │              └─ Device/Build/image (rootfs 编译 + 镜像合成)
                     └─ install: $(LINUX_DIR)/.image
                          └─ +make -C image compile install TARGET_BUILD=  (kernel-build.mk:176-177)
```

关键路径：
- **kernel-build.mk:157**: `compile: $(LINUX_DIR)/.modules` → `+$(MAKE) -C image compile TARGET_BUILD=`
- **kernel-build.mk:176**: `install: $(LINUX_DIR)/.image` → `+$(MAKE) -C image compile install TARGET_BUILD=`

这意味着内核镜像编译和目标镜像编译都通过 `target/linux/mediatek/image/Makefile` 执行。`TARGET_BUILD=1` 让 include/image.mk 走 `Device/Build/*` 分支。

### 1.3 Image 构建目标入口：`BuildImage`

`include/image.mk:965-1017` 定义了 `BuildImage`，是所有 target/linux/<board>/image/Makefile 的顶层框架：

```makefile
define BuildImage

  compile:

  install: install-images
    $(call Image/Manifest)
endef
```

## 2. Kernel 镜像管道：从源码到 FIT Image

### 2.1 管线概述

MT7981 Filogic 默认的内核镜像管线定义在 `target/linux/mediatek/image/Makefile:17-34`：

```makefile
define Device/Default
  KERNEL_NAME := Image                          # aarch64 Linux Image (非 vmlinux)
  KERNEL = kernel-bin | lzma | \
    fit lzma $$(KDIR)/image-$$(firstword $$(DEVICE_DTS)).dtb
  KERNEL_INITRAMFS = kernel-bin | lzma | \
    fit lzma $$(KDIR)/image-$$(firstword $$(DEVICE_DTS)).dtb with-initrd
  KERNEL_LOADADDR = 0x48000000                  # Filogic 默认加载地址
  FILESYSTEMS := squashfs erofs
  IMAGES := sysupgrade.bin
  IMAGE/sysupgrade.bin := append-kernel | pad-to 128k | append-rootfs | \
    pad-rootfs | append-metadata
endef
```

**管线语法**：`|` 分隔的每一段对应一个 `Build/<命令>` 或 `Image/Build/<命令>`，按顺序执行，上一段的输出作为下一段的输入（`$@`）。

### 2.2 管线拆解

#### 第一段：`kernel-bin`

`include/image-commands.mk:539-542`：
```makefile
define Build/kernel-bin
  rm -f $@
  cp $< $@                     # 从 $(KDIR)/vmlinux 或 Image 复制到 $@
endef
```

`$<` 是 `Device/Build/kernel` 规则的第一个依赖：`$(KDIR)/$(KERNEL_NAME):: image_prepare` → `$(call Kernel/Compile)` → Linux 源码的 `arch/arm64/boot/Image`（aarch64 输出文件恰好就叫 `Image`，不是 `vmlinux`）。

#### 第二段：`lzma`

`include/image-commands.mk:591-598`：
```makefile
define Build/lzma
  $(call Build/lzma-no-dict,-lc1 -lp2 -pb2 $(1))
endef
define Build/lzma-no-dict
  $(STAGING_DIR_HOST)/bin/lzma e $@ $(1) $@.new
  @mv $@.new $@
endef
```

使用 `$(STAGING_DIR_HOST)/bin/lzma`（主机工具，不是目标工具）对 Image 压缩。`STAGING_DIR_HOST` 是交叉编译工具链的安装目录（`build_dir/host`）。

#### 第三段：`fit lzma $(KDIR)/image-$(DTS).dtb`

`include/image-commands.mk:464-467`：
```makefile
define Build/fit
  $(call Build/fit-its,$(1))
  $(call Build/fit-image,$(1))
endef
```

两步：
1. `fit-its` → 调用 `scripts/mkits.sh` 生成 `.its` (Image Tree Source) 文件
2. `fit-image` → 调用 `mkimage -f $@.its $@.new` 生成 `.itb` (FIT Image Blob)

`Device/Default` 中传参 `lzma` 和 `$(KDIR)/image-$(firstword $(DEVICE_DTS)).dtb`，对应 `Build/fit-its` 的参数解析：

`include/image-commands.mk:433-455`：
```makefile
define Build/fit-its
  # $(1) = "lzma", $(2) = dtb path (optional), $(3) = with-rootfs/with-initrd
  $(TOPDIR)/scripts/mkits.sh \
    -D $(DEVICE_NAME) -o $@.its \
    -C $(word 1,$(1)) \         # 压缩类型: lzma / gzip / none
    $(if $(word 2,$(1)),-d $(KERNEL_BUILD_DIR)/image-$$(basename $(word 2,$(1))),) \
    -a $(KERNEL_LOADADDR) -e $(if $(KERNEL_ENTRY),$(KERNEL_ENTRY),$(KERNEL_LOADADDR)) \
    -c $(if $(DEVICE_DTS_CONFIG),$(DEVICE_DTS_CONFIG),"config-1") \
    -A $(LINUX_KARCH) -v $(LINUX_VERSION) \
    ...
endef
```

`mkits.sh` (`scripts/mkits.sh:1-244`) 生成 DTS 格式的 `.its` 文件，其中关键节点：

```dts
/dts-v1/;
/ {
  images {
    kernel@1 {
      description = "ARM64 OpenWrt Linux-6.12";
      data = /incbin/("Image.lzma");          # 内核压缩镜像
      type = "kernel";
      arch = "arm64";
      os = "linux";
      compression = "lzma";
      load = <0x48000000>;                   # KERNEL_LOADADDR
      entry = <0x48000000>;
    };
    fdt@1 {
      description = ...;
      data = /incbin/("mt7981b-xxx.dtb");    # 编译后的 DTB
      type = "flat_dt";
    };
    // with-rootfs 时还有 rootfs@1 节点
  };
  configurations {
    default = "config-1";
    config-1 {
      kernel = "kernel@1";
      fdt = "fdt@1";
      // with-rootfs 时: loadables = "rootfs@1"
    };
  };
};
```

`mkimage -f $@.its $@.new` 将 `.its` 编译为 `.itb`（U-Boot FIT 格式），它是一个环形结构：kernel + DTB（还可以内嵌 rootfs）打包在一起。

### 2.3 DTB 编译：Image/BuildDTB

`include/image.mk:228-246`：
```makefile
define Image/BuildDTB/sub
  $(TARGET_CROSS)cpp -nostdinc -x assembler-with-cpp \
    -I$(DTS_DIR) -I$(DTS_DIR)/include \
    -I$(LINUX_DIR)/include/ \
    -I$(LINUX_DIR)/scripts/dtc/include-prefixes \
    -undef -D__DTS__ \
    -o $(2).tmp $(1)
  $(LINUX_DIR)/scripts/dtc/dtc -O dtb \
    -i$(dir $(1)) \
    -o $(2) $(2).tmp
  $(RM) $(2).tmp
endef
```

DTS 源文件在 `target/linux/mediatek/dts/mt7981b-*.dts`，编译输出到 `build_dir/linux-aarch64_cortex-a53_musl/linux-6.12/arch/arm64/boot/dts/mediatek/mt7981b-*.dtb`，然后在 Device/Build/kernel 阶段通过 `Build/append-dtb` 拼入 FIT。

### 2.4 最终内核输出

`Device/Default` 中 `KERNEL := kernel-bin | lzma | fit lzma ...dtb`，管线输出文件为：
- `$(KDIR)/image-mt7981b-<device>.itb` — FIT Image，包含压缩内核 + DTB（+ 可选 rootfs）
- 该文件在 `Device/Build/kernel:743` 通过 `cp $^ $@` 复制到 `$(BIN_DIR)/$(KERNEL_IMAGE)` = `$(BIN_DIR)/openwrt-mediatek-filogic-<device>-kernel.bin`

## 3. Root Filesystem 构建：从 target-dir 到 squashfs 镜像

### 3.1 target-dir 的准备

**第一步：基础文件系统** (`include/rootfs.mk:71-101` 的 `prepare_rootfs`)：
1. 从 `$(TARGET_DIR_ORIG)` 复制到 `$(TARGET_DIR)`（ORIG = 编译后的原始根文件系统快照）
2. 标记设备节点 `/dev`（`mknod`）
3. 运行所有包 postinst 脚本（`Package/<pkg>/postinst`）
4. 对 opkg 状态文件修正（将 `Status: user` 改为 `ok`）

**第二步：per-device 定制** (`include/image.mk:400-423` 的 `target-dir-%`)：
- 如果 `CONFIG_TARGET_PER_DEVICE_ROOTFS` 开启，每个设备有独立 rootfs（通过不同 DEVICE_PACKAGES 组合产生不同包集合）
- 包通过 `opkg`（或 `apk`）安装到 `$(TARGET_DIR)`

**第三步：$(TOPDIR)/files 覆盖** (`include/image.mk:423`)：
- `$(call prepare_rootfs,$(TARGET_DIR),$(TOPDIR)/files)` — 如果存在 `$(TOPDIR)/files/` 目录，其内容覆盖 target-dir（用于用户自定义配置）

### 3.2 文件系统镜像生成

`target/linux/mediatek/image/Makefile:25` 定义 `FILESYSTEMS := squashfs erofs`（filogic 不默认构建 jffs2 / ubifs 等）。

**SquashFS 生成** (`include/image.mk:282-303`)：
```makefile
define Image/mkfs/squashfs-common
  $(STAGING_DIR_HOST)/bin/mksquashfs4 \
    $(call mkfs_target_dir,$(1)) $@ \
    -nopad -noappend -root-owned \
    -comp $(SQUASHFSCOMP) $(SQUASHFSOPT)
endef
# SQUASHFSCOMP: gzip (默认); 如果 CONFIG_SQUASHFS_XZ=y 则为 xz
# SQUASHFS_BLOCK_SIZE: 128k (CONFIG_TARGET_SQUASHFS_BLOCK_SIZE)k
# SQUASHFSOPT: -p '/dev d 755 0 0' -p '/dev/console c 600 0 0 5 1'
```

输出：`build_dir/linux-.../root.squashfs`（MD5-based id 后缀）

**EROFS 生成** (`include/image.mk:327-331`)：
```makefile
define Image/mkfs/erofs
  env -u SOURCE_DATE_EPOCH $(STAGING_DIR_HOST)/bin/mkfs.erofs \
    -z$(EROFSCOMP) -C$(EROFS_PCLUSTERSIZE) $(EROFSOPT) \
    $@ $(call mkfs_target_dir,$(1))
endef
# EROFSCOMP: lz4hc,12 (默认); CONFIG_EROFS_FS_ZIP_LZMA 时为 lzma,109
```

### 3.3 UBI/UBIFS：NAND 设备的特殊处理

MT7981 的 NAND 设备不使用纯 squashfs 镜像，而是用 **UBI + UBIFS** 或 **UBI + squashfs**（`KERNEL_IN_UBI := 1`）。相关宏定义在 `target/linux/mediatek/image/filogic.mk:5-9`：

```makefile
define Image/Prepare
  rm -f $(KDIR)/ubi_mark
  echo -ne '\xde\xad\xc0\xde' > $(KDIR)/ubi_mark   # UBI 坏块标记
endef
```

UBI 镜像的生成由 `Build/ubinize-image` 或 `Build/append-ubi` 触发，不是简单的 squashfs。以下是 `scripts/ubinize-image.sh:14-98` 的卷结构逻辑：

```bash
ubivol() {                                    # 输出 ubinize.cfg 卷条目
  echo "[$name]"
  echo "mode=ubi"
  echo "vol_id=$volid"
  echo "vol_type=$voltype"                    # dynamic (可动态调整) 或 static
  echo "vol_name=$name"
  echo "vol_size=${size}"
}
# 最终卷布局 (典型):
# vol_id=0: ubootenv  (1MiB, dynamic)
# vol_id=1: ubootenv2 (1MiB, dynamic)
# vol_id=2: kernel    (kernel in UBI, static, 可选 KERNEL_IN_UBI=1)
# vol_id=3: rootfs    (autoresize for UBIFS; 固定 1k-block-aligned for squashfs)
# vol_id=4: rootfs_data (autoresize for squashfs, JFFS2 兼容层)
```

## 4. Device/Profile 框架与 filogic.mk 设备定义

### 4.1 Device 框架工作原理

`include/image.mk:428-963` 定义了 OpenWrt 的设备抽象框架，是理解镜像构建的核心：

```
Device/InitProfile    → 初始化 PROFILES, DEVICE_TITLE, DEVICE_PACKAGES (空)
Device/Init          → 初始化所有变量默认值 (KERNEL, IMAGES, IMAGE_SIZE, ARTIFACTS...)
Device/Default       → 从 target/linux/<board>/image/Makefile 的 Device/Default 继承
Device/<name>        → 用户定义的设备实际参数 (DTS, 分区, 镜像命令...)
Device/Check         → 检查 .config 中该设备是否启用
Device/Build         → 展开为具体 make 规则 (Device/Build/kernel, Device/Build/image, Device/Build/artifact)
```

**`Device/Init` 默认变量** (`include/image.mk:467-552`)：
```makefile
DEVICE_NAME := $(1)           # 设备名，如 "openwrt_one"
KERNEL :=                     # 内核镜像管线命令（默认来自 Device/Default）
IMAGES :=                     # 要生成的镜像文件列表
ARTIFACTS :=                  # 附属产物（preloader.bin, bl31-uboot.fip...）
IMAGE_SIZE :=                 # 最大镜像大小（分区大小）
NAND_SIZE :=                  # NAND Flash 总大小
KERNEL_IN_UBI :=              # 是否将 kernel 打包进 UBI 卷
UBOOTENV_IN_UBI :=             # 是否将 ubootenv 打包进 UBI
DEVICE_DTS :=                  # 要编译的 DTS 文件名（无后缀）
DEVICE_PACKAGES :=             # 额外安装的包列表
UBOOT_PATH := $(STAGING_DIR_IMAGE)/uboot-$(1)  # 不适用于 filogic
```

### 4.2 filogic.mk 的 Build 命令扩展

`target/linux/mediatek/image/filogic.mk:1-140` 在 include/image-commands.mk 之外定义了 MT7981 专用 Build 命令：

```makefile
define Build/mt7981-bl2
  # cat STAGING_DIR_IMAGE/mt7981-<arg1>-bl2.img >> $@
  # arg1 = TFA 变体名，如 "spim-nand-ddr3"
  cat $(STAGING_DIR_IMAGE)/mt7981-$1-bl2.img >> $@
endef

define Build/mt7981-bl31-uboot
  # cat STAGING_DIR_IMAGE/mt7981_<arg1>-u-boot.fip >> $@
  # arg1 = U-Boot 变体名，如 "openwrt_one-snand"
  cat $(STAGING_DIR_IMAGE)/mt7981_$1-u-boot.fip >> $@
endef
```

**命名不对称性**：
- BL2 使用 **连字符** 风格（来自 TFA 包：`mt7981-spim-nand-ddr3-bl2.img`）
- FIP 使用 **下划线 + mt7981_ 前缀** 风格（来自 U-Boot 包：`mt7981_openwrt_one-snand-u-boot.fip`）

### 4.3 设备定义范例：openwrt_one（旗舰参考设计）

`target/linux/mediatek/image/filogic.mk:2861-2905`：
```makefile
define Device/openwrt_one
  DEVICE_VENDOR := OpenWrt
  DEVICE_MODEL := One
  DEVICE_DTS := mt7981b-openwrt-one
  DEVICE_DTS_DIR := ../dts
  DEVICE_DTC_FLAGS := --pad 4096          # DTB 4KB 对齐
  DEVICE_DTS_LOADADDR := 0x43f00000       # DTB 加载地址

  KERNEL_LOADADDR := 0x44000000            # 比默认值 0x48000000 低（openwrt_one 设计）
  KERNEL := kernel-bin | gzip             # 注意：不是 lzma，是 gzip
  KERNEL_INITRAMFS := kernel-bin | lzma | \
    fit lzma $$(KDIR)/image-$$(firstword $$(DEVICE_DTS)).dtb with-initrd | pad-to 64k
  KERNEL_INITRAMFS_SUFFIX := .itb

  KERNEL_IN_UBI := 1                     # kernel 打入 UBI 卷
  UBOOTENV_IN_UBI := 1                   # ubootenv 打入 UBI 卷

  IMAGES := sysupgrade.itb
  IMAGE/sysupgrade.itb := append-kernel | \
    fit gzip $$(KDIR)/image-$$(firstword $$(DEVICE_DTS)).dtb \
    external-with-rootfs | pad-rootfs | append-metadata
  # external-with-rootfs: FIT 中 rootfs 作为独立子镜像，通过 fitblk 暴露为块设备

  UBINIZE_OPTS := -E 5                   # UBI 擦除对齐
  BLOCKSIZE := 128k
  PAGESIZE := 2048

  # 引导加载程序产物
  ARTIFACTS := nor-preloader.bin nor-bl31-uboot.fip \
    snand-preloader.bin snand-bl31-uboot.fip \
    factory.ubi snand-factory.bin nor-factory.bin

  # SPI-NOR 介质 (bl2 连字符 + FIP 下划线)
  ARTIFACT/nor-preloader.bin    := mt7981-bl2 nor-ddr4
  ARTIFACT/nor-bl31-uboot.fip  := mt7981-bl31-uboot openwrt_one-nor

  # SPI-NAND 介质
  ARTIFACT/snand-preloader.bin  := mt7981-bl2 spim-nand-ubi-ddr4
  ARTIFACT/snand-bl31-uboot.fip:= mt7981-bl31-uboot openwrt_one-snand

  # UBI factory 镜像（kernel+rootfs 一起打包）
  ARTIFACT/factory.ubi         := ubinize-image fit squashfs-sysupgrade.itb

  # snand-factory.bin: 重复 bl2 (256k/512k/768k/1M) + ubinize-image
  ARTIFACT/snand-factory.bin   := mt7981-bl2 spim-nand-ubi-ddr4 | pad-to 256k | \
    mt7981-bl2 spim-nand-ubi-ddr4 | pad-to 512k | \
    mt7981-bl2 spim-nand-ubi-ddr4 | pad-to 768k | \
    mt7981-bl2 spim-nand-ubi-ddr4 | pad-to 1024k | \
    ubinize-image fit squashfs-sysupgrade.itb

  # nor-factory.bin: nor-bl2 + eeprom + nor-bl31-uboot.fip + initramfs

endef
```

**关键理解**：
- `sysupgrade.itb` 是 **不含 rootfs 的 FIT**（`external-with-rootfs`），rootfs 从 UBI:fit 卷加载

## 5. 组合镜像合成：sysupgrade.itb / factory.ubi / sysupgrade.bin

### 5.1 `IMAGE/sysupgrade.itb` 管线

对于 `openwrt_one`：
```
IMAGE/sysupgrade.itb := append-kernel | fit gzip ...dtb external-with-rootfs | pad-rootfs | append-metadata
```

管线展开：
1. `append-kernel` → `dd if=$(IMAGE_KERNEL) of=$@` — 将 FIT kernel.itb 写入 sysupgrade.itb
2. `fit gzip ...dtb external-with-rootfs` — **注意**：这里不是 `fit`，而是 `fit` 已经被 `Device/Default` 的 `KERNEL := kernel-bin | gzip | fit lzma dtb` 管线处理过了，所以 `append-kernel` 追加的是**已经封装好的 FIT 文件**
3. `pad-rootfs` → padjffs2 填充 rootfs 到块边界
4. `append-metadata` → fwtool 添加 JSON 元数据 + sha256sum

### 5.2 `append-metadata` 命令

`include/image-commands.mk:91-100`：
```makefile
define Build/append-metadata
  $(if $(SUPPORTED_DEVICES),-echo $(call metadata_json) | fwtool -I - $@)
  # fwtool -I -: 将 JSON metadata 追加到镜像文件末尾
  sha256sum "$@" | cut -d" " -f1 > "$@.sha256sum"
  # 如果有签名密钥：usign 签名 + ucert 包装 + fwtool -S 追加
  [ ! -s "$(BUILD_KEY)" -o ! -s "$(BUILD_KEY).ucert" -o ! -s "$@" ] || { \
    cp "$(BUILD_KEY).ucert" "$@.ucert" ;\
    usign -S -m "$@" -s "$(BUILD_KEY)" -x "$@.sig" ;\
    ucert -A -c "$@.ucert" -x "$@.sig" ;\
    fwtool -S "$@.ucert" "$@" ;\
  }
endef
```

## 7. Flash 分区布局与 DTS 描述（以 openwrt_one 为例）

本章以旗舰参考设计 `openwrt_one`（`target/linux/mediatek/dts/mt7981b-openwrt-one.dts`）为核心，描述 MT7981 的 Flash 分区布局。详细的可视化布局见第 13 节。

### 7.1 SPI-NAND Flash 分区布局（以 openwrt_one 为例）

`mt7981b-openwrt-one.dts`（第 322-345 行）：

```
flash@0 (spi-nand, 总容量 256MB):
  partition@0       "bl2"        0x000000 - 0x100000  (1MB, 只读, BootROM 加载 BL2)
  partition@580000   "ubi"        0x100000 - 0x10000000 (255MB, UBI 卷)
                       └─ volumes:
                           ubi-volume-fit (volname="fit") → kernel FIT 镜像
                           ubi-volume-rootfs (squashfs)
                           ubi-volume-ubootenv × 2 (各 1MiB)
```

**布局特点**：openwrt_one 的 SPI-NAND 布局非常精简——仅 `bl2` + `ubi` 两个分区。U-Boot 环境变量与 rootfs 一起打包进 UBI 卷，kernel FIT 存放在 UBI:fit 卷。没有独立的 u-boot-env / factory / fip 分区；U-Boot 可能嵌入 UBI:fit（通过 mkimage "firmware" 子镜像）或由 BootROM 特殊加载路径处理。

> **变体差异**：多数商业 NAND 设备（如 abt_asr3000、MT7981-rfb）的 DTS 布局更复杂——`partition@0 "bl2"` + `partition@100000 "u-boot-env"` + `partition@180000 "art"` + `partition@280000 "factory"` + `partition@380000 "fip"` + `partition@580000 "ubi"`。FIP 是独立的 raw MTD 分区（`partition@380000 "fip"`，128KB），与 UBI 并列。

### 7.2 SPI-NOR Flash 布局（Dual Flash 设备）

`mt7981b-openwrt-one.dts`（第 365-407 行）：

```
flash@1 (spi-nor):
  partition@0        "bl2-nor"   0x00000 - 0x40000    (256KB, BootROM 加载 BL2)
  partition@40000    "factory"   0x40000 - 0xC0000   (512KB, 校准数据 MAC/Board ID)
  partition@100000   "fip-nor"   0x100000 - 0x180000 (512KB, FIP 镜像)
  partition@180000   "recovery"  0x180000 - 0xE00000  (12.5MB, 恢复 kernel)
```

**fip-nor 分区内容**：`mt7981_openwrt_one-nor-u-boot.fip`（xz 压缩: BL31 + U-Boot proper）。

**双 Flash 启动流程**（openwrt_one Dual Flash）：
1. BootROM 加载 SPI-NAND BL2 → 启动主系统
2. 也可切换至 SPI-NOR：BL2_NOR → FIP_NOR → Recovery kernel（用于紧急恢复）
3. NOR 分区主要用于：出厂校准数据存储、Recovery 镜像、FIP 备份

### 7.4 sysupgrade 升级路径

`target/linux/mediatek/filogic/base-files/lib/upgrade/platform.sh:98-159`：

```bash

  local board=$(board_name)
  case "$board" in
  openwrt,one|abt,asr3000|mediatek,mt7981-rfb|...)
    fit_do_upgrade "$1"        # FIT 镜像升级
    ;;
  acer,predator-w6|glinet,gl-mt2500|...)
    emmc_do_upgrade "$1"       # eMMC 设备升级
    ;;
  asus,rt-ax52|asus,rt-ax57m|...)

    nand_do_upgrade "$1"       # 厂商 UBI NAND 升级
    ;;
  *)
    default_do_upgrade "$1"     # 直接mtd write
    ;;
  esac

```

`fit_do_upgrade` (`/lib/upgrade/fit.sh`) 流程：
1. `fwtool -q -i /tmp/sysupgrade.meta "$1"` — 读取镜像元数据验证兼容性
2. `fwtool_check_signature` — 如果签名开启，验证 usign 签名
3. `fit info` — 读取 FIT 信息
4. `fit flash kernel` — 将 FIT 中的 kernel 写入 UBI:fit 卷（或 MTD 分区）
5. `fitblk release` — 释放 FIT rootfs 块设备
6. `fit rootfs layout` — 确定 rootfs 在 UBI 卷中的位置
7. `nand_do_upgrade` 或 `emmc_do_upgrade` — 写入 rootfs

## 8. fitblk：内核如何从 FIT 镜像中引导 rootfs

### 8.1 设计背景

传统的 OpenWrt 镜像中，kernel 和 rootfs 是独立的文件/分区。但 Filogic 平台引入了一个巧妙的设计：**将 rootfs 嵌入到 FIT 镜像内部**，通过 `fitblk` 机制在运行时暴露为块设备。

### 8.2 内核配置

`target/linux/mediatek/filogic/config-6.12`：
```
CONFIG_MTD_UBI=y                    # UBI 子系统
CONFIG_MTD_UBI_BLOCK=y              # UBI 块设备（将 UBI 卷转为块设备）
CONFIG_UIMAGE_FIT_BLK=y             # FIT 块设备驱动（关键！）
```

`drivers/block/fitblk.c`（内核补丁 `target/linux/generic/pending-6.12/510-block-add-uImage.FIT-subimage-block-driver.patch`）：该驱动解析 U-Boot FIT 镜像中的子镜像（`"rootfs"` 节点），将其内容作为块设备暴露。

### 8.3 FIT 镜像中的 rootfs 节点

`Build/fit-its` 中的 `rootfs` 节点 (`scripts/mkits.sh:143-161`)：
```dts
rootfs@1 {
  description = "ARM64 OpenWrt rootfs";
  data = /incbin/("rootfs.squashfs.pagesync");  # 带 pagesync 头
  type = "filesystem";
  arch = "arm64";
  compression = "none";
};
```

**为什么需要 `.pagesync`**：`mkfs.squashfs` 输出 `rootfs.squashfs`，但 UBI 块设备需要 4KB 对齐。`scripts/mkits.sh:85-88` 检测：如果 rootfs 不是 4KB 对齐，追加 `.pagesync` blob（4096 字节的 0x00 填充）使总长度对齐。

### 8.4 运行时引导流程

```
U-Boot:
  ubi part ubi 0
  ubifsload virt 0:fit 0x48000000 openwrt_one-sysupgrade.itb
  bootm 0x48000000                    # 启动 FIT 镜像

Linux (boot params from FDT):
  /chosen/rootdisk = <&ubi_fit_volume> # phandle 指向 UBI 卷
  MTD UBI:ubi 块设备被 mtdblock 驱动创建
  fitblk 驱动:
    - 解析 FIT 中的 rootfs@1 子镜像
    - 将其内容作为 /dev/fit0 (块设备) 暴露
  mount /dev/fit0 /                  # squashfs 根文件系统
```

`package/utils/fitblk` 的用户态工具 (`fitblk` 可执行文件) 和 `/lib/upgrade/fit.sh` 负责在引导时正确释放块设备、处理镜像布局。

## 9. 元数据与 sysupgrade 兼容性验证

### 9.1 fwtool 的 metadata 格式

`fwtool` 源码来自 `openwrt/project/fwtool.git`（作为 host 包构建），安装在 `$(STAGING_DIR_HOST)/bin/fwtool`。

镜像末尾的 metadata 布局：
```
[镜像数据] [JSON 元数据] [sha256sum (64字节 hex + \n)]
```

**JSON 元数据追加** (`fwtool -I - $@`)：
- `metadata_version`: "1.1"（当前版本）
- `compat_version`: "1.0"（设备兼容性版本）
- `supported_devices`: 支持的设备 ID 列表（用于 sysupgrade 校验）
- `version`: OpenWrt 版本信息
- `supported_devices` vs `new_supported_devices`: compat_version 迁移机制

**签名追加**（如果存在签名密钥）：
1. `usign -S -m "$@" -s "$BUILD_KEY"` → 产生 `$@.sig`
2. `ucert -A -c "$@.ucert" -x "$@.sig"` → 将签名包装为 ucert 证书
3. `fwtool -S "$@.ucert" "$@"` → 追加到镜像

### 9.2 设备兼容性版本（compat_version）

`target/linux/mediatek/image/filogic.mk` 中的设备可声明 `DEVICE_COMPAT_VERSION := 1.1`，并附带 `DEVICE_COMPAT_MESSAGE`：

```makefile
define Device/routerich_ax3000
  ...
  DEVICE_COMPAT_VERSION := 1.1
  DEVICE_COMPAT_MESSAGE := Partition layout has been changed. Bootloader MUST be \
    upgraded to avoid data corruption and getting bricked.
endef
```

sysupgrade 时，`fwtool -i /tmp/sysupgrade.meta` 读取 `compat_version`：
- 主版本不同（1.x → 2.x）→ 拒绝升级（需要重新刷机）
- 次版本不同 → 警告但允许（sysupgrade -n 建议）
- `FORCE` (`-F`) 可强制跳过

## 13. 镜像与 Flash 分区布局可视化

### 13.1 理解两类镜像的本质区别

MT7981 的镜像分为两大类，理解它们的设计意图是看懂布局的前提：

| 类型 | 用途 | 包含内容 | 烧录方式 |
|------|------|---------|---------|
| **sysupgrade 镜像** | 在线升级 | 仅有 kernel + rootfs（无 BL2/FIP） | `fit_do_upgrade` / `nand_do_upgrade` 写入 UBI 卷 |
| **factory 镜像** | 工厂量产 / 全量烧录 | BL2 + FIP + kernel + rootfs（全套） | 全区或分区裸写（用编程器或 BootROM 下载模式） |

**sysupgrade 镜像不包含 bootloader**，因为 BootROM 和 BL2 / FIP 出厂就烧好了，升级固件不需要重刷它们。这样做的好处是：
- 升级包体积小（不含 ~8MB 的 BL2+FIP）
- 升级时不会意外刷坏 bootloader 导致变砖

**factory 镜像包含全套组件**，因为工厂量产时需要一次性把完整系统写入空白 Flash。

### 13.2 Flash 物理布局（MT7981 各启动介质）

以下布局数据来自 `mt7981b-openwrt-one.dts`（SPI-NAND / SPI-NOR / eMMC）及 `filogic.mk` 的 `Build/mt798x-gpt` 分区表定义。

#### SPI-NAND Flash（最常见，大多数商业路由器使用，以 openwrt_one 为例）

布局数据来自 `target/linux/mediatek/dts/mt7981b-openwrt-one.dts`（第 322-345 行）：

```
┌──────────────────────────────────────────────────────────────────────────────────┐
│  MT7981 SPI-NAND Flash (openwrt_one, 总容量 256MB)                          │
│                                                                                          │
│  ┌──────────────┬─────────────────────────────────────────────────────────────┐  │
│  │ 0x000000     │ partition@0 "bl2" (1MB, 只读)                          │  │
│  │  0 ~ 1MB     │ BootROM 从本分区起始地址加载 BL2 到 SRAM              │  │
│  │              │ ┌──────────────────────────────────────────────┐     │  │
│  │              │ │ mt7981-spim-nand-ubi-ddr4-bl2.img          │     │  │
│  │              │ │ (ATF 构建, mkimage 包装头, 含 BL2 入口)     │     │  │
│  │              │ └──────────────────────────────────────────────┘     │  │
│  │              └─────────────────────────────────────────────────────┘  │
│  ├──────────────┼─────────────────────────────────────────────────────────────┤  │
│  │ 0x100000     │ partition@580000 "ubi" (255MB)                         │  │
│  │  1 ~ 256MB   │ ┌──────────────────────────────────────────────────┐    │  │
│  │              │ │ UBI Volume: fit (volname="fit")             │    │  │
│  │              │ │ ┌──────────────────────────────────────────┐ │    │  │
│  │              │ │ │ kernel FIT (Image.lzma + DTB)        │ │    │  │
│  │              │ │ ├──────────────────────────────────────────┤ │    │  │
│  │              │ │ │ U-Boot proper (nt-fw, 嵌入 firmware    │ │    │  │
│  │              │ │ │         子镜像, 替代独立 FIP 分区)       │ │    │  │
│  │              │ │ │ BL31 / soc-fw (EL3 Runtime)            │ │    │  │
│  │              │ │ └──────────────────────────────────────────┘ │    │  │
│  │              │ └──────────────────────────────────────────────────┘    │  │
│  │              │ ┌──────────────────────────────────────────────────┐    │  │
│  │              │ │ UBI Volume: rootfs (squashfs, autoresize)     │    │  │
│  │              │ └──────────────────────────────────────────────────┘    │  │
│  │              │ ┌──────────────────────────────────────────────────┐    │  │
│  │              │ │ UBI Volume: rootfs_data (JFFS2 overlay)       │    │  │
│  │              │ └──────────────────────────────────────────────────┘    │  │
│  │              │ ┌──────────────────────────────────────────────────┐    │  │
│  │              │ │ UBI Volume: ubootenv × 2 (各 1MiB)              │    │  │
│  │              │ └──────────────────────────────────────────────────┘    │  │
│  └──────────────┴─────────────────────────────────────────────────────────────┘  │
└──────────────────────────────────────────────────────────────────────────────────┘
```

**关键理解**：openwrt_one 的 SPI-NAND 布局非常精简——仅 `partition@0 "bl2"` + `partition@580000 "ubi"` 两个分区。**没有独立的 FIP 分区**；U-Boot 可能嵌入 UBI:fit volume 中的 firmware 子镜像（通过 mkimage 打包），或由 BootROM 特殊加载路径处理。BootROM 按顺序从 BL2 → UBI → fitblk 依次加载：
1. BootROM 从 `partition@0 (bl2)` 加载 BL2 到 SRAM
2. BL2 从 UBI:fit 加载 kernel FIT（含 U-Boot）
3. U-Boot 挂载 UBI，从 `UBI:fit` 读取 kernel FIT
4. fitblk 将 rootfs 子镜像暴露为块设备

> **变体差异**：`openwrt_one` 的 SPI-NAND DTS 布局更简化（`mt7981b-openwrt-one.dts`），只有 `partition@0 "bl2"` + `partition@580000 "ubi"` 两个分区，无独立的 u-boot-env / factory / fip 分区——U-Boot 环境变量与 rootfs 一起打包进 UBI，U-Boot 可能嵌入 UBI:fit 或通过其他机制加载。

**SPI-NAND 启动时序**（openwrt_one）：
```
BootROM → BL2 (bl2 分区) → UBI:fit (kernel FIT, 含 U-Boot) → fitblk → rootfs
```

### 13.4 启动流程中的组件定位图

以下展示三种典型启动路径中，每个阶段读取哪个 Flash 区域：

```
路径 A: SPI-NAND 启动（abt_asr3000 / 多数商业 NAND 设备）
══════════════════════════════════════════════════════════════

  Flash MTD 分区                组件                           加载到
  ──── ────────────                           ────                           ──────
  partition@0 (bl2)    →    BL2 (mt7981-spim-nand-*-bl2.img)    SRAM
       ↓
  partition@380000 (fip) →    FIP (mt7981-*-u-boot.fip)           DRAM
  (raw MTD, 不是 UBI)         ├─ BL31 (soc-fw, EL3 Runtime)           │
                              └─ U-Boot proper (nt-fw)                  │
       ↓                                                                 │
  BL31 (在 FIP 内部)   →    EL3 Runtime                                  DRAM
       ↓                                                                 │
  U-Boot proper          →    Bootloader                                   DRAM
  (FIP 中的 nt-fw)            │                                             │
       ↓                                                                 │
  partition@580000 (ubi) →    UBI:fit (kernel FIT)                    DRAM
  (raw MTD, UBI 层)          ├─ kernel (Image.lzma)                       │
  │                           ├─ DTB (mt7981b-xxx.dtb)                       │
  │                           └─ (可选) rootfs@1 (external-with-rootfs)     │
       ↓                                                                 │
  UBI:rootfs 卷           →    squashfs → fitblk → /dev/fit0     / (rootfs)
       ↓                                                                 │
  /dev/ubi0_0             →    rootfs_data (JFFS2 overlay)         /overlay
```

**路径 A 启动时序**：
1. **BootROM** 从 `partition@0 (bl2)` 读取 BL2 到 SRAM（BootROM 硬编码偏移）
2. **BL2** 从 `partition@380000 (fip)` 读取 FIP（BL2 知道 fip 分区的固定偏移）
3. **FIP** 中 BL31 初始化 EL3 环境，**U-Boot proper** 接管
4. **U-Boot** 使用 `ubi part ubi` 挂载 UBI，从 `UBI:fit` 读取 kernel FIT
5. **fitblk** 驱动读取 `/chosen/rootdisk` phandle，将 FIT 中的 rootfs 子镜像暴露为 `/dev/fit0` 块设备
6. **Linux** 从 `/dev/fit0` (squashfs) 挂载根文件系统

**关键区别**：FIP 是 raw MTD 分区（`partition@380000 "fip"`），**不在 UBI 内**。BL2 通过 NAND Romcode 直接访问 raw 分区；UBI 是 Linux 内核的 FTL 层，需等 Linux 启动后才能使用。

**FIP 位置因设备而异**：
- **SNAND 设备**（abt_asr3000 等）：FIP 是独立的 raw MTD 分区 `partition@380000 "fip"`（128KB）
- **openwrt_one snand**：无独立 FIP 分区，U-Boot 可能嵌入 UBI:fit volume 中的 firmware 子镜像
- **NOR 设备**（openwrt_one nor）：FIP 是独立的 `partition@100000 "fip-nor"`（512KB）
- **eMMC 设备**：FIP 存放在 eMMC Boot Partition 2

**为什么 sysupgrade 镜像不需要 BL2/FIP？** 因为：
1. 升级时 BootROM → BL2 → FIP → U-Boot 的路径已经固化
2. 升级只替换 kernel FIT（写入 UBI:fit 卷）和 rootfs（UBI:rootfs 卷）
3. 如果升级包含 BL2/FIP，一旦中途断电，设备将变砖（无 bootloader 恢复）

**为什么 snand-factory.bin 没有独立 FIP？** 因为 openwrt_one snand 变体的 DTS 没有定义独立 `fip` 分区，U-Boot 可能被嵌入 UBI:fit volume（通过 mkimage "firmware" 子镜像）。而 abt_asr3000 等设备的 DTS 定义了 `partition@380000 "fip"`，snan-factory.bin 若基于此类设备则会包含独立 FIP 分区。

## 14. 总结

1. **BootROM → BL2 → BL31 → U-Boot (FIP) → Kernel FIT**：MT7981 的五段启动链全部从源码构建，无预编译二进制
2. **ATF 源码** → `mt7981-*-bl2.img` + `mt7981-*-bl31.bin` → 写入 Flash BL2 分区
3. **U-Boot 源码 + fiptool** → `mt7981_<device>-u-boot.fip`（FIP 包含 BL31 + U-Boot proper）→ 写入 Flash FIP 分区
4. **Kernel**: Linux 源码 → `Image` → lzma 压缩 → FIT 打包（含 DTB，可选内嵌 rootfs）→ 写入 UBI fit 卷或独立分区
5. **Rootfs**: `TARGET_DIR` → `mksquashfs4` → squashfs 镜像 → 可内嵌在 FIT（`external-with-rootfs`）或放入 UBI rootfs 卷
6. **sysupgrade.itb**: FIT 格式，含 kernel + DTB，rootfs 通过 fitblk 从 UBI 卷加载
7. **factory.ubi**: 完整 UBI 镜像（含 kernel FIT + rootfs），用于工厂批量烧录
8. **元数据**: fwtool 追加 JSON + sha256（可选 usign 签名）用于 sysupgrade 兼容性校验
9. **Device/Profile 框架** 是 OpenWrt 镜像构建的核心抽象：通过 `Device/<name>` 定义声明式管线，`BuildImage` 统一执行所有设备
10. **sysupgrade 镜像不含 BL2/FIP**，只含 kernel + rootfs；factory 镜像含全套（BL2 + FIP + kernel + rootfs）；两者设计意图严格分离
