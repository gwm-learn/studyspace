# netifd（网络接口守护进程）

## 一、概述

### 1.1 什么是 netifd？
netifd（Network Interface Daemon）是 OpenWrt 系统中最核心的网络管理守护进程，负责管理所有网络接口（WAN、LAN、WiFi、VLAN、Bridge、PPP 等）的配置、状态、协议处理与事件响应。

### 1.2 主要功能
- **配置管理**：读取 UCI 配置文件（`/etc/config/network`），将其转化为内核可识别的网络命令（ip、ifconfig、brctl、vconfig 等）。
- **接口与设备管理**：管理物理接口（eth0、wlan0）和逻辑接口（VLAN、Bridge、PPP 虚拟接口）。
- **协议处理**：支持 DHCP 客户端、PPPoE、静态 IP、6in4、WWAN（4G/5G 拨号）等 WAN 协议。
- **状态机与事件驱动**：每个接口都有独立的状态机，根据内核事件（link up/down）、协议事件（DHCP 获取成功）等进行状态切换。
- **ubus API 服务**：通过 ubus 对外提供网络状态查询、配置修改、接口控制等 RPC 接口。
- **热插拔（hotplug）支持**：响应内核的 netlink 事件，自动处理接口的插拔、WiFi 接口的创建与删除。

### 1.3 在 OpenWrt 架构中的位置
netifd 是 OpenWrt 网络子系统的“大脑”，与以下核心组件紧密协作：

| 组件 | 作用 | 与 netifd 的交互 |
|------|------|------------------|
| **UCI** | 统一配置接口 | netifd 读取 `/etc/config/network`，并将运行时状态写回 UCI 缓存 |
| **ubus** | 进程间通信（IPC） | netifd 注册为 ubus 服务，提供 RPC 方法供 LuCI、procd、TR069 等调用 |
| **procd** | 进程管理与守护 | procd 启动、监控、重启 netifd 进程，确保网络服务高可用 |
| **内核** | 网络栈与驱动 | netifd 通过 netlink（libnl）与内核通信，配置接口、路由、地址等 |
| **hotplug** | 热插拔脚本 | netifd 触发 `/etc/hotplug.d/iface/` 中的脚本，执行自定义动作 |

### 1.4 为什么需要 netifd？
- **统一管理**：将分散的 `ifconfig`、`route`、`brctl` 等命令封装成统一的配置模型。
- **动态响应**：实时响应网络变化（如网线插拔、WiFi 连接断开），自动重配网络。
- **配置持久化**：UCI 配置与运行时状态分离，重启后配置不丢失。
- **服务化 API**：通过 ubus 提供编程接口，方便第三方应用（如 LuCI、TR069）集成。

## 二、架构设计

### 2.1 整体架构图
```
+-------------------+     读取/更新       +-------------------+
|     UCI 配置       |<------------------>|   netifd 核心      |
|  /etc/config/network|                   | (主循环、状态机、   |
+-------------------+                   |  事件处理器)        |
         ^                                       |
         | 通过 libuci                          | 通过 ubus 注册服务
         |                                       v
+-------------------+                   +-------------------+
|   ubus 总线        |<---------------->|  ubus 方法        |
| (进程间通信)       |   调用/事件        | (network.*)       |
+-------------------+                   +-------------------+
         ^                                       |
         | 调用/订阅                             | 配置下发、状态上报
         v                                       v
+-------------------+                   +-------------------+
|   外部调用者        |                   |   内核网络栈       |
| (LuCI、TR069、CLI) |                   | (netlink、ioctl)  |
+-------------------+                   +-------------------+
```

### 2.2 核心模块
1. **配置解析器（config parser）**：解析 UCI 的 `network` 配置，生成内部数据结构（interface、device、protocol）。
2. **设备管理器（device manager）**：管理物理设备（如 eth0）和虚拟设备（如 br-lan），跟踪设备状态（UP/DOWN、链路状态）。
3. **接口管理器（interface manager）**：管理逻辑接口（如 lan、wan），每个接口绑定一个设备和一个协议，维护接口状态机。
4. **协议处理器（protocol handler）**：实现 DHCP、PPPoE、Static 等协议的客户端逻辑，负责协议状态的获取与更新。
5. **事件循环（event loop）**：基于 libubox 的 uloop，监听文件描述符、定时器、信号，处理 netlink 事件、ubus 请求等。
6. **ubus 接口（ubus interface）**：将内部方法暴露为 ubus 对象（`network`、`network.interface`、`network.device`），供外部调用。
7. **热插拔触发器（hotplug trigger）**：根据接口状态变化，执行 `/etc/hotplug.d/iface/` 中的用户脚本。

### 2.3 与内核的交互
netifd 通过 **netlink**（内核与用户空间通信的 socket）监听内核事件并下发配置：
- **NETLINK_ROUTE**：监听接口新增、删除、链路状态变化、地址变更等。
- **NETLINK_NETFILTER**：监听防火墙规则变化（较少使用）。
- 通过 `libnl` 库发送命令创建桥接、VLAN、设置 MTU、添加路由等。

## 三、核心概念

### 3.1 设备（Device）
设备代表一个物理或虚拟的网络设备，如 eth0、wlan0、br-lan、vlan10。
- **物理设备**：由内核驱动创建，netifd 负责将其“UP”并配置基本参数（MTU、MAC 地址）。
- **虚拟设备**：由 netifd 根据配置创建，如桥接设备、VLAN 设备。

配置示例（UCI）：
```uci
config device 'lan_dev'
    option name 'br-lan'
    option type 'bridge'
    list ports 'eth0'
    list ports 'eth1'
```

### 3.2 接口（Interface）
接口是逻辑概念，代表一个可配置的网络单元，如 LAN、WAN、GUEST。一个接口必须绑定一个设备，并指定一个协议（DHCP、static、pppoe 等）。

配置示例（UCI）：
```uci
config interface 'lan'
    option device 'br-lan'
    option proto 'static'
    option ipaddr '192.168.1.1'
    option netmask '255.255.255.0'
```

### 3.3 协议（Protocol）
协议定义接口如何获取 IP 地址、路由等网络参数。netifd 内置多种协议处理器：
- **static**：静态 IP
- **dhcp**：DHCP 客户端（自动获取 IP）
- **pppoe**：PPPoE 拨号
- **ppp**：通用 PPP 协议（用于 3G/4G/5G 拨号）
- **6in4**、**6to4**：IPv6 隧道协议
- **none**：仅启用接口，不配置 IP

### 3.4 状态机（State Machine）
每个接口都有一个状态机，状态包括：
- **down**：接口未启用
- **up**：接口已启用，但协议未就绪
- **running**：协议已就绪（如 DHCP 获取到 IP）
- **error**：协议失败（如拨号失败）

状态转换由事件驱动（链路 UP、DHCP 成功、用户操作等）。

## 四、配置详解

### 4.1 UCI 配置文件结构
`/etc/config/network` 是 netifd 的唯一配置来源，包含以下节类型：

#### 4.1.1 `config interface 'section_name'`
定义逻辑接口。
- `option device`：绑定的设备名
- `option proto`：协议类型
- `option ipaddr` / `option netmask` / `option gateway`：静态 IP 参数
- `option username` / `option password`：PPPoE 认证信息
- `option ifname`（旧版）：直接指定物理接口（不推荐，应使用 device）

#### 4.1.2 `config device 'section_name'`
定义设备（桥接、VLAN）。
- `option name`：设备名称
- `option type`：设备类型（`bridge`、`vlan`）
- `list ports`：桥接的物理端口列表
- `option vid`：VLAN ID

#### 4.1.3 `config route 'section_name'`
静态路由配置。
- `option interface`：出口接口
- `option target`：目标网络
- `option gateway`：下一跳

#### 4.1.4 `config rule 'section_name'`
策略路由规则。

### 4.2 典型配置示例

#### 4.2.1 简单 LAN + WAN（DHCP）
```uci
config interface 'loopback'
    option device 'lo'
    option proto 'static'
    option ipaddr '127.0.0.1'
    option netmask '255.0.0.0'

config device 'lan_dev'
    option name 'br-lan'
    option type 'bridge'
    list ports 'eth0'
    list ports 'eth1'

config interface 'lan'
    option device 'br-lan'
    option proto 'static'
    option ipaddr '192.168.1.1'
    option netmask '255.255.255.0'

config interface 'wan'
    option device 'eth2'
    option proto 'dhcp'
```

#### 4.2.2 PPPoE 拨号
```uci
config interface 'wan'
    option device 'eth2'
    option proto 'pppoe'
    option username 'user@isp'
    option password 'passwd'
    option mtu '1492'
    option keepalive '3 5'
```

#### 4.2.3 VLAN 划分
```uci
config device 'vlan10_dev'
    option name 'eth0.10'
    option type 'vlan'
    option ifname 'eth0'
    option vid '10'

config interface 'vlan10'
    option device 'eth0.10'
    option proto 'static'
    option ipaddr '192.168.10.1'
    option netmask '255.255.255.0'
```

### 4.3 配置生效流程
1. **读取配置**：netifd 启动时，通过 libuci 读取 `/etc/config/network`。
2. **生成内部对象**：将 UCI section 转换为 device、interface、protocol 实例。
3. **配置内核**：根据 device 配置创建桥接/VLAN，将接口 UP。
4. **启动协议**：根据 interface 配置启动对应协议（如 DHCP 客户端）。
5. **状态更新**：协议成功后，设置接口 IP、路由，并触发 hotplug 脚本。

## 五、ubus API

netifd 通过 ubus 提供丰富的 RPC 方法，方便外部程序查询和控制网络状态。

### 5.1 主要对象与方法

#### `network`
- `network.restart`：重启整个网络服务（相当于 `/etc/init.d/network restart`）。
- `network.reload`：重载配置（不重启接口）。

#### `network.interface`
- `network.interface.status`：获取指定接口的详细状态（包括 IP、路由、协议信息）。
- `network.interface.up` / `network.interface.down`：启用/禁用指定接口。
- `network.interface.prepare`：准备接口（重新启动协议）。
- `network.interface.add_device` / `network.interface.remove_device`：动态添加/移除接口绑定的设备。

#### `network.device`
- `network.device.status`：获取设备状态（链路、统计信息）。
- `network.device.set_state`：设置设备状态（测试用途）。

### 5.2 调用示例
```bash
# 查看 lan 接口状态
ubus call network.interface.lan status

# 启用 wan 接口
ubus call network.interface.wan up

# 重启整个网络
ubus call network restart
```

### 5.3 事件订阅
netifd 会通过 ubus 发布事件，其他服务可订阅以响应网络变化：
- `interface.<事件>`：如 `interface.up`、`interface.down`、`interface.state`。
- `device.<事件>`：如 `device.add`、`device.remove`、`device.link`。

订阅示例：
```bash
ubus listen 'interface.*'
```

## 六、事件与热插拔

### 6.1 事件来源
1. **内核 netlink 事件**：接口链路状态变化、地址变更、新设备出现。
2. **协议事件**：DHCP 获取成功/失败、PPPoE 拨号成功/断开。
3. **用户操作**：通过 ubus 调用 up/down。
4. **定时器事件**：DHCP 租期更新、PPPoE 心跳保活。

### 6.2 热插拔脚本
当接口状态变化时，netifd 会自动执行 `/etc/hotplug.d/iface/` 目录下的脚本，脚本按数字顺序执行。

脚本环境变量：
- `ACTION`：动作（`ifup`、`ifdown`、`ifupdate`）
- `INTERFACE`：接口名（如 `lan`、`wan`）
- `DEVICE`：设备名（如 `br-lan`）
- `STATUS`：接口状态（`up`、`down`、`running`）

示例脚本 `/etc/hotplug.d/iface/99-my-script`：
```bash
#!/bin/sh
[ "$ACTION" = "ifup" ] && logger "接口 $INTERFACE 已启动"
```

### 6.3 自定义处理
可通过热插拔脚本实现：
- 接口 UP 后启动特定服务
- 接口 DOWN 后发送通知
- 根据 IP 变化更新 DDNS

## 七、协议处理器扩展

netifd 支持插件式协议处理器，开发者可自定义协议。

### 7.1 内置协议
- **static**：最简单，直接配置 IP。
- **dhcp**：使用 `udhcpc` 客户端获取 IP。
- **pppoe**：使用 `pppoe` 客户端（基于 `ppp`）。
- **ppp**：通用 PPP 协议，用于 3G/4G/5G 模块拨号。
- **6in4**、**6to4**、**6rd**：IPv6 隧道。
- **none**：仅启用接口，不配置 IP。

### 7.2 自定义协议
可通过编写 shell 脚本或 C 插件实现。协议脚本位于 `/lib/netifd/proto/`，每个协议一个脚本。

示例：自定义协议脚本 `myproto.sh`：
```bash
#!/bin/sh

proto_init_update() { ... }
proto_run_command() { ... }
proto_close() { ... }

proto_myproto_setup() {
    # 配置逻辑
}

proto_myproto_teardown() {
    # 清理逻辑
}
```

然后在 UCI 配置中指定 `proto 'myproto'`。

## 八、调试与日志

### 8.1 日志查看
netifd 的日志通过 `logread` 查看，通常标记为 `netifd`。
```bash
logread | grep netifd
```

### 8.2 启用详细调试
编辑 `/etc/config/system`，增加 netifd 的调试级别：
```uci
config system
    option log_level 'debug'
```
然后重启 netifd：`/etc/init.d/network restart`

### 8.3 命令行工具
- `ubus call network.interface.<name> status`：查看接口详细状态。
- `ip link show`、`ip addr show`：查看内核接口状态。
- `brctl show`：查看桥接状态。
- `logread -f`：实时跟踪日志。

### 8.4 常见问题排查
1. **接口无法 UP**：检查设备是否存在（`ip link show`）、驱动是否加载。
2. **DHCP 获取不到 IP**：检查物理链路、DHCP 服务器、防火墙规则。
3. **PPPoE 拨号失败**：检查用户名密码、MTU 设置、ISP 状态。
4. **桥接不工作**：检查端口是否已加入桥接（`brctl show br-lan`）。
5. **VLAN 不通**：检查交换机端口的 VLAN 配置、VLAN ID 是否一致。

## 九、与 procd 的集成

### 9.1 进程管理
netifd 由 procd 托管，其启动脚本为 `/etc/init.d/network`。该脚本定义了一个 procd 服务实例，支持 `start`、`stop`、`restart`、`reload` 等操作。

### 9.2 高可用保障
procd 为 netifd 启用 `respawn` 机制，若 netifd 异常退出，procd 会自动重启它，确保网络服务不间断。

### 9.3 配置依赖
procd 在启动 netifd 之前，会确保 `ubusd`、`logd` 等依赖服务已就绪。

## 十、面试常见问题

### 10.1 基础概念
1. **netifd 的作用是什么？**
   > netifd 是 OpenWrt 的网络接口守护进程，负责管理所有网络接口的配置、状态、协议处理与事件响应，是 OpenWrt 网络子系统的核心。

2. **netifd 与 UCI、ubus、procd 的关系？**
   > netifd 读取 UCI 配置，通过 ubus 提供 API，由 procd 托管并监控。三者构成 OpenWrt 配置-通信-管理的闭环。

3. **设备（device）与接口（interface）的区别？**
   > 设备是物理或虚拟的网络设备（如 eth0、br-lan），接口是逻辑配置单元（如 lan、wan），一个接口绑定一个设备并指定一个协议。

### 10.2 配置与调试
4. **如何配置一个基于 VLAN 的多 SSID 网络？**
   > 创建 VLAN 设备，将 VLAN 设备绑定到不同的接口，每个接口配置不同的 IP 子网，并在无线配置中指定对应的网络接口。

5. **如何通过 ubus 查看某个接口的详细状态？**
   > `ubus call network.interface.lan status`

6. **接口一直处于“down”状态可能的原因？**
   > 设备不存在、驱动未加载、物理链路断开、配置错误（如 device 名称错误）。

### 10.3 高级问题
7. **netifd 如何实现动态响应网络变化？**
   > 通过 netlink 监听内核事件（如链路状态变化），通过事件循环触发状态机转换，并执行相应的配置更新。

8. **如何扩展 netifd 以支持新的拨号协议？**
   > 编写协议脚本放在 `/lib/netifd/proto/` 目录下，实现 `setup`、`teardown` 等函数，并在 UCI 配置中指定 `proto` 为新协议名。

9. **netifd 与传统的 ifup/ifdown 脚本相比有什么优势？**
   > 统一配置模型、状态机管理、事件驱动、ubus API、热插拔支持，更适合嵌入式环境。

10. **在 CPE 产品中，netifd 如何保障网络稳定性？**
    > 通过 procd 的 respawn 机制自动重启异常进程；通过状态机自动重拨（如 PPPoE 断线重连）；通过热插拔脚本触发故障恢复动作。
